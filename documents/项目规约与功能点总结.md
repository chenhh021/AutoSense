# AutoSense 项目规约与功能点总结

整理日期：2026-09-05  
依据：`.specify/` 及其关联的 `specs/001-iot-auto-diagnosis/` 文档。  
说明：本文件整理现行文档要求、历史验证记录及文档差异，不代表本次重新执行了实现验收。

根据 `.specify` 及其关联文档，AutoSense 的核心定位是：**通过自然语言对话识别设备问题，在明确授权和受控流程下执行诊断、修复与复检；无法自动解决时，提供人工步骤或售后渠道。**

`.specify` 保存项目级开发规约、模板和流程配置；具体功能规格由 [.specify/feature.json](../.specify/feature.json) 指向 `specs/001-iot-auto-diagnosis/`。以下依据这些文件整理，采用后续澄清后的要求；文档中的旧描述、未完成评审和实现记录会单独说明。

首先，各类规约文件的职责如下：

| 文件或目录 | 作用 |
|---|---|
| `.specify/memory/constitution.md` | 项目章程，规定技术栈、编码纪律、质量门和修订规则 |
| `.specify/templates/` | 规格、计划、任务、检查清单和章程模板 |
| `.specify/workflows/speckit/workflow.yml` | 规定从需求规格到实现的工作流及评审节点 |
| `.specify/scripts/powershell/` | 创建特性、定位当前特性、准备计划和任务、检查前置文件、解析模板 |
| `.specify/feature.json` | 指定当前特性的文档目录 |
| `.specify/integration.json`、`integrations/` | Spec Kit 与 Claude、Codex 的集成配置、版本和安装文件记录 |
| `specs/.../spec.md` | 用户故事、功能需求、边界情况、成功标准和澄清记录 |
| `specs/.../plan.md`、`research.md` | 技术方案、实现约束和选型理由 |
| `specs/.../data-model.md`、`contracts/` | 数据模型、状态机、API 和错误语义 |
| `specs/.../tasks.md`、`validation/` | 当前增量任务及历史验证证据 |

模板中的示例功能和占位内容不属于 AutoSense 的实际需求。

项目的最高层开发约束来自 [项目章程](../.specify/memory/constitution.md)，版本为 **1.0.0**，批准和最后修订日期均为 **2026-08-21**。

| 原则 | 具体要求 |
|---|---|
| **Java 21 基线** | 开发、编译、CI 和生产运行时统一使用 Java 21；可合理使用 record、sealed 类型、模式匹配、虚拟线程等；禁止依赖预览特性和非标准 API |
| **Spring Boot 框架规范** | 固定使用 Spring Boot 3.5.3；依赖注入必须采用构造器注入；配置通过 `@ConfigurationProperties` 或 `@Value` 读取；不得绕过 Spring 容器手动创建受管 Bean；新增 starter 或升级框架前必须评估兼容性 |
| **数据访问纪律** | 关系数据库使用 MySQL，持久层使用 MyBatis-Flex；业务代码不得直接拼接 SQL；缓存使用 Redis，缓存键必须有明确命名和过期策略；Redis 不得充当持久化存储 |
| **AI 集成规范** | 所有大模型及 AI 能力调用通过 LangChain4j；业务代码不得直接调用模型厂商原生 HTTP 接口或 SDK；模型提供商、名称、温度等由配置注入 |
| **配置外部化** | 数据库、Redis、大模型、第三方 HTTP 服务等连接信息和凭据必须由配置导入，并由 `@ConfigurationProperties` 承载；源码不得硬编码外部地址、端口、密钥或令牌；真实凭据不得提交版本库 |

这些技术选型是约束性要求。替换组件需要走章程修订流程：提出修改及理由、通过评审、更新章程和影响报告；涉及已有代码时，还要提供迁移计划。

章程版本采用语义化版本：删除或不兼容重定义原则提升主版本，新增原则或实质性扩充提升次版本，措辞澄清提升修订版本。所有 PR 都需要核对章程合规性，违反原则的复杂设计必须给出书面理由。

开发流程要求**先形成规格，再规划和拆任务，最后实现**。章程禁止跳过规格直接编码；工作流文件进一步设置了两个评审节点：

```text
specify：形成需求规格
   ↓
评审规格，通过后继续；拒绝则终止
   ↓
plan：形成实现计划及设计文档
   ↓
评审计划，通过后继续；拒绝则终止
   ↓
tasks：生成任务清单
   ↓
implement：执行任务
```

模板对交付物还有以下要求：

- 用户故事按 P1、P2 等优先级组织，并说明业务价值和独立验证方式。
- 验收场景采用 Given / When / Then，描述前提、操作和预期结果。
- 功能要求使用 `FR-xxx` 编号，成功标准使用 `SC-xxx` 编号。
- 规格需要覆盖异常场景、依赖和假设，未确定内容应明确标记。
- 计划在研究前和设计后都要检查章程合规性。
- 任务按用户故事组织，写明任务编号、精确文件路径及依赖。
- `[P]` 表示任务在前置条件满足、没有文件冲突和依赖冲突时可以并行。
- 基础设施阶段完成后，才能进入依赖它的用户故事。
- 需求质量检查清单中的 `[x]` 表示评审通过，**不表示实现完成**；实现流程不得自行修改评审勾选状态。
- 提交前必须通过 `./mvnw verify` 或等效构建，且测试全部通过。

通用任务模板把“新增测试任务”列为按需项；但当前 SN 绑定增量的任务文件明确要求测试先行：先确认测试因缺少目标行为而失败，再完成实现。不能把模板示例中的 TDD 要求直接当作章程原文。依据：[工作流](../.specify/workflows/speckit/workflow.yml)、[任务模板](../.specify/templates/tasks-template.md)、[检查清单模板](../.specify/templates/checklist-template.md)。

业务范围由 [功能规格](../specs/001-iot-auto-diagnosis/spec.md) 定义，共 **3 个用户故事、27 条功能要求和 9 项成功标准**。

| 用户故事 | 优先级 | 要交付的能力 |
|---|---|---|
| US1：自动诊断与修复闭环 | P1 | 理解用户问题、定位设备、采集状态、判定故障、确认修复、执行和复检；包含按 SN 添加设备 |
| US2：无法自动修复时的用户引导 | P2 | 已知操作步骤时提供人工指引；步骤不明时提供附近售后信息或官方客服 |
| US3：用户账号体系与权限控制 | P1 | 注册、登录、当前用户信息、注销、用户角色、管理员最小管理能力及设备和对话隔离 |

经过澄清，当前交付范围已收敛为：

- 诊断设备只包含**智能灯泡**：模拟器类型 `LITE`，型号 `LA001` 单色灯泡和 `LB001` 彩光灯泡。
- 路由器、空调等待模拟器扩展对应型号后接入。
- 设备交互通过 HTTP 调用外部 `deviceSimulator`，本项目不开发模拟器本体或设备固件。
- 平台按 SN 绑定模拟器中已有的设备，不再代为创建设备。
- 售后查询首期使用固定 Mock 网点数据；实际地图搜索作为后续扩展。
- 型号特异性问题首期并入常识回答；型号专用 RAG 后续补充。
- 规格定义的交付形式仍是 API 和文字对话；语音、图片输入不在本期范围。
- 对话及诊断过程长期保留，原先的 90 天清理策略已撤销。
- 所有改变设备状态的操作都要确认，确认范围已从“可能中断服务的操作”扩大到“全部状态修改”。

下面按业务流程展开这些功能要求。

用户首先需要拥有账号并登录，相关要求为 **FR-015、FR-022～FR-027**。

注册时提交账号、密码和确认密码。账号必须为 4～32 位，仅允许字母、数字、下划线，且全平台唯一；密码为 8～64 位，必须同时包含字母和数字，两次输入必须一致。昵称默认取账号，密码使用 BCrypt 散列保存，接口和日志都不得输出明文密码或密码散列。

注册接口不能让用户指定角色。新账号固定为普通用户 `user`，即使请求夹带角色字段，也不能获得管理员权限。

登录成功后颁发不透明随机 Token。设计采用 32 字节密码学随机数编码为 Base64URL，存入 Redis；客户端通过 `Authorization: Bearer <token>` 携带。Token 有效期为 **7 天滚动续期**，每次成功鉴权延长有效期。

账号不存在、密码错误和账号被禁用时，登录均返回统一认证失败，不向调用方区分原因。注销会立即删除当前 Token；Token 过期或注销后再次使用，一律按未登录处理。

开发环境保留 `user-{id}` 形式的令牌，但受 `AUTH_DEV_MODE` 显式控制，真实 Redis Token 始终优先解析，生产必须关闭开发令牌模式。

权限方面：

| 身份 | 可以执行的操作 | 数据范围 |
|---|---|---|
| 未登录用户 | 注册、登录 | 不能访问受保护业务接口 |
| 普通用户 | 使用诊断服务，管理本人会话和已定义的设备功能 | 仅本人设备和对话 |
| 管理员 | 普通用户能力，加用户列表和禁用/启用能力 | 设备和对话仍仅限本人 |

管理员用户列表支持分页、按账号或昵称搜索，默认排除禁用用户，可通过参数包含禁用用户。禁用采用逻辑删除标记，立即撤销该用户全部 Token，并阻止再次登录；重新启用后需要重新登录，旧 Token 不恢复。

管理员不能禁用自身。当前管理范围不包含修改角色或重置他人密码。初始管理员由幂等种子数据创建，文档要求首次部署后修改初始密码。依据：[用户 API 契约](../specs/001-iot-auto-diagnosis/contracts/user-api.md)。

设备接入是最近一次修改最细的部分，主要对应 **FR-020**，并与 **FR-003、FR-004、FR-015** 衔接。

用户添加设备只提交：

```json
{
  "sn": "LITE123456789",
  "name": "客厅灯"
}
```

SN 必须原样满足 `^[A-Z0-9]{4}[0-9]{9}$`，即前 4 位为大写字母或数字，后 9 位为数字，总长 13 位。不得自动去除空白、转换大小写或删除字符。显示名称必填、不能全为空白，最长 64 字符。

绑定流程规定为：

```text
校验 SN 和名称
   ↓
检查平台是否已有该 SN
   ↓
在数据库事务之外调用模拟器按 SN 查询
   ↓
确认设备存在，且稳定元数据完整
   ↓
使用短事务插入绑定记录
   ↓
返回平台设备信息及动态计算的 supported
```

其中有几项必须遵守的约束：

- **SN 全平台唯一**，唯一键不能包含 `user_id`。
- 同用户重复绑定、不同用户重复绑定，均返回相同冲突结果，不泄露原绑定用户。
- 重复预检查命中时，不再调用模拟器。
- 并发请求最终由数据库 `uk_device_sn` 唯一约束裁决，不能只依赖“先查再插”。
- 查询模拟器期间不持有数据库长事务。
- 不允许覆盖已有绑定，也不允许因绑定而在模拟器新增设备。
- 类型、型号和模拟器设备 ID 以查询结果为准，不能接受用户自行覆盖。

平台显示名称和模拟器原始名称分开保存；用户输入“客厅灯”，模拟器返回其他名称时，列表仍显示“客厅灯”。

**可以绑定不等于可以诊断。** 查询到的设备即使类型或型号暂不支持，也应绑定成功并返回 `supported:false`；之后发起诊断时，在读取状态和执行操作之前明确拒绝。`supported` 根据当前配置动态计算，不写入数据库，因此后续增加适配器后不需要重新绑定。

绑定错误必须区分：

| 情况 | 返回语义 | 是否写入绑定 |
|---|---|---|
| SN、名称不合法，或上游参数错误 | `400 BAD_REQUEST` | 否 |
| 查询返回 `exists:false` | `404 DEVICE_NOT_FOUND`，设备不存在或不在线 | 否 |
| SN 已绑定，或并发插入发生唯一冲突 | `409 DEVICE_ALREADY_BOUND` | 否 |
| 上游 5xx、连接失败、超时、畸形响应 | `503 DEVICE_SERVICE_UNAVAILABLE` | 否 |
| 设备存在且元数据完整，但不支持诊断 | `201`，`supported:false` | 是 |

不能把上游超时或 5xx 当成“设备不存在”，也不能向客户端透传底层内部异常。依据：[研究结论 R24～R26](../specs/001-iot-auto-diagnosis/research.md)、[诊断与设备 API 契约](../specs/001-iot-auto-diagnosis/contracts/diagnosis-api.md)。

收到自然语言问题后，系统先识别意图，对应 **FR-001、FR-002、FR-019**。

| 意图 | 处理路径 | 设备访问约束 |
|---|---|---|
| 常识问题 | 直接回答 | 不调用设备 |
| 设备诊断或自动操作 | 进入诊断修复流程 | 完成定位、权限和支持性检查后推进 |
| 型号特异性问题 | 首期并入常识回答 | 不因回答而操作设备 |
| 售后网点查询 | 独立查询路径 | 无需先诊断设备 |
| 意图不明确 | 追问澄清 | 不触碰设备 |

进入设备流程后，需要提取设备类型、问题表现，以及用户提供的复现方式。信息不足时必须追问，不能盲目猜测。

设备定位只在当前用户的设备范围内进行。存在多台候选设备时，必须列出候选并让用户确认唯一目标。一次描述涉及多台设备或多个问题时，应拆分逐个处理，或者引导用户一次处理一个；规格尚未固定唯一拆分算法。

诊断和修复闭环对应 **FR-003～FR-009、FR-014、FR-016、FR-017**。

```text
识别问题
  → 定位唯一设备
  → 检查归属和类型、型号支持性
  → 获取设备互斥锁
  → 采集修复前状态
  → 规则判定并检索知识
  → 请求用户确认
  → 执行白名单动作
  → 采集修复后状态
  → 输出复检结论
```

系统采用**确定性状态机编排**。LLM 用于意图分类、语义分析、诊断推理和文字生成；设备写操作由状态机调用适配器，不能由 LLM 自由触发工具调用。

故障规则放在 YAML 设备注册表中，每条规则包含条件、结论类型，以及修复动作和参数或人工步骤引用。规则按顺序匹配，首条命中生效：

| 规则结果 | 系统行为 |
|---|---|
| `AUTO_REPAIRABLE` | 形成可执行方案，等待用户确认 |
| `MANUAL_ONLY` | 返回明确的人工操作步骤 |
| `AFTERSALES` | 转入售后指引 |
| `NORMAL` | 给出无异常结论和观察建议，不强行修复 |

例如，亮度异常低可映射为调整亮度的方案；硬件故障类状态可映射为人工处理。**规则决定处理类别，知识库补充方案和操作说明**，规则显式引用的知识优先。

读取诊断信息属于探测，不需要单独的操作确认；调亮度、调色温、调颜色、启动设备等状态修改，都必须先确认。用户拒绝时，应结束本轮自动修复并记录原因，不能继续执行。

修复结束后，无论命令成功还是失败，都需要复检。成功响应不能直接等同于“问题已修复”，结论需要结合修复后的设备状态。

失败策略是：

- 一旦动作失败，立即停止后续动作。
- 不得自动重试。
- 重新读取当前状态。
- 如实告知失败情况和设备现状。
- 转入人工步骤或售后分支。

设备离线或诊断请求超时时，要停止诊断，提示检查电源和网络，不得伪造诊断结果或继续修复。同一台设备同时只能有一个进行中的修复会话，冲突请求返回 `DEVICE_BUSY`。用户后续主动发起新一轮，与同一轮内自动重试是不同的行为。

无法自动修复时，对应 **FR-010、FR-011**，系统必须给用户可执行的下一步。

如果知道明确人工步骤，需说明无法远程修复的原因，并给出分步指引。如果不知道明确步骤，则根据用户位置返回售后网点名称、地址和联系方式。

位置优先由用户在会话中提供，或经授权获取；缺少位置时可进入等待位置的状态。无可用位置、没有合适网点或查询无法提供结果时，使用配置中的品牌官方客服渠道兜底。

售后查询首期使用固定 Mock 数据，不能让 LLM 现场编造地址和电话。研究方案设有默认 10 公里搜索半径，后续可替换查询实现为地图服务；具体位置优先级和结果数量等细节，在质量检查清单中仍有待确认项。

对话管理对应 **FR-013、FR-018**，其边界是“长期对话线程，线程内可进行多轮诊断”。

- 每个对话由唯一 `sessionId` 标识。
- 用户可以新建对话、查看本人历史列表、继续已有对话。
- 历史列表按最近更新时间倒序。
- 终态对话可以继续，新问题沿用原 `sessionId` 开启新一轮。
- 每轮新增问题报告，轮次号递增，并重新执行必要的定位和锁获取。
- 完整聊天消息、诊断快照和动作日志长期保存。
- LLM 默认只看到最近 **20 条消息**，超出窗口的消息仍可被用户查询。
- Redis 中的对话记忆过期后，可以从 MySQL 重建最近消息窗口。
- 用户离开或会话超时后，应保留可查询的状态和结论，不得悬空执行未经确认的动作。

数据模型中的主流程从 `CREATED → ROUTING` 开始，等待用户的状态包括：

| 状态 | 等待内容 |
|---|---|
| `CLARIFYING` | 补充问题或澄清意图 |
| `DEVICE_CONFIRMING` | 确认目标设备 |
| `CONFIRMING_REPAIR` | 确认是否执行状态修改 |
| `AWAITING_LOCATION` | 提供售后查询位置 |

状态迁移和修复动作均要求留痕。依据：[数据模型与状态机](../specs/001-iot-auto-diagnosis/data-model.md)。

接口交互中的流式协议对应 **FR-021**。创建会话和追加消息的 POST 请求直接返回 SSE，不另建订阅端点。

| 事件 | 内容 |
|---|---|
| `token` | LLM 生成的增量文本 |
| `status` | 状态机迁移，包括会话 ID 和当前状态 |
| `awaiting` | 等待用户输入及提示内容 |
| `conclusion` | 本轮终态结论 |
| `error` | 统一业务错误信息 |

每条流只覆盖本次 POST 的处理过程。进入等待输入状态或终态后，服务端主动关闭流；用户下一次回复发起新 POST，再建立新流。确认修复之后，执行、复检和结论在该次确认请求的流内继续推送。

断线不补发事件，不依赖 `Last-Event-ID` 恢复；调用方通过 GET 查询会话当前状态和结论。普通查询接口返回 JSON。

公开业务接口可以归纳为下表，统一前缀为 `/api/v1`：

| 方法和路径 | 功能 | 返回形式 |
|---|---|---|
| `POST /users/register` | 注册 | JSON，成功 201 |
| `POST /users/login` | 登录 | JSON，Token 和用户信息 |
| `GET /users/me` | 当前用户信息 | JSON |
| `POST /users/logout` | 注销 | 成功 204 |
| `GET /admin/users` | 管理员分页搜索用户 | JSON |
| `PUT /admin/users/{id}/status` | 禁用或启用用户 | JSON |
| `POST /devices` | 按 SN 绑定设备 | JSON，成功 201 |
| `GET /devices` | 本人设备列表 | JSON |
| `POST /sessions` | 新建对话 | SSE |
| `POST /sessions/{id}/messages` | 澄清、确认、补位置、继续对话 | SSE |
| `GET /sessions` | 本人历史对话列表 | JSON |
| `GET /sessions/{id}` | 当前状态及结论 | JSON |
| `GET /sessions/{id}/messages` | 完整聊天记录 | JSON |

结论类型包括 `FIXED`、`UNFIXED_MANUAL_GUIDE`、`UNFIXED_AFTERSALES`、`DEVICE_UNREACHABLE`、`ANSWERED` 和 `AFTERSALES_PROVIDED`，可附带修复前后状态、人工步骤或售后网点数组。

当前契约没有定义设备解绑、设备删除、对话删除或用户资料编辑接口，不能仅凭实体字段推导这些功能已经纳入规约。

数据规约强调**长期事实、实时设备状态和临时上下文分别管理**。

| MySQL 实体 | 保存内容 |
|---|---|
| `user` | 账号、密码散列、资料字段、角色、禁用标记 |
| `device` | 用户归属、SN、平台名称、模拟器名称、设备与类型型号标识 |
| `repair_session` | 对话归属、目标设备、当前状态、结论 |
| `problem_report` | 每轮原始问题、意图、设备类型、症状、复现方式和澄清记录 |
| `diagnostic_snapshot` | 每轮修复前 `PRE`、修复后 `POST` 的诊断数据 |
| `repair_action_log` | 动作或状态迁移、参数、结果和说明 |
| `repair_knowledge` | 问题特征、方案正文、动作码、人工步骤 |
| `chat_message` | 消息角色、正文和时间 |

设备绑定表只保存稳定元数据，不保存模拟器返回的 `state`、`running_status` 或模拟器创建、更新时间。平台自身的绑定时间可以保存。诊断时获取的实时状态可以存入独立快照表，因此“绑定表不保存运行状态”不影响诊断追溯。

用户表保留用户给定的 camelCase 列名，MyBatis-Flex 实体需显式映射，不能通过修改全局驼峰规则影响其他实体。

Redis 设计约定为：

| 键 | 用途 | 过期策略 |
|---|---|---|
| `autosense:session:{sessionId}` | 活跃会话上下文 | 30 分钟滚动 |
| `autosense:lock:device:{deviceId}` | 设备互斥锁 | 10 分钟，推进时续期，终态释放 |
| `autosense:chatmemory:{sessionId}` | LLM 最近消息窗口 | 30 分钟滚动 |
| `autosense:token:{token}` | 登录令牌 | 7 天滚动 |
| `autosense:usertokens:{userId}` | 用户全部令牌索引 | 7 天滚动 |
| `autosense:rag:*` | 知识向量索引 | 研究文档声明显式重建、不设 TTL；与章程的关系仍需同步说明 |

知识库设计以 MySQL 为权威来源，规划使用 LangChain4j Redis Embedding Store 和 RediSearch 做向量检索，知识变更后同步重建索引。这是**设计要求**；本次整理前的源码检查中，当前知识检索仍以关键词匹配为主，不能把设计方案直接当作完整实现。

设备扩展能力对应 **FR-012、SC-006**。新增类型应通过设备适配器、YAML 注册条目、诊断字段、动作白名单、故障规则和知识内容完成，核心诊断状态机无需修改。外部设备服务也通过 `DeviceServiceClient` 隔离，未来接真实服务时更换实现。

数据库迁移有明确约束：修改 `CREATE TABLE IF NOT EXISTS` 不会升级已有表，必须提供前向迁移脚本。迁移应保留旧行，先检查 SN 和旧类型、型号能否可靠回填；不能回填时报告并中止，不能静默删除数据、重建生产库或用 `continue-on-error` 跳过失败。依据：[实现计划](../specs/001-iot-auto-diagnosis/plan.md)、[端到端验证指南](../specs/001-iot-auto-diagnosis/quickstart.md)。

验收目标分为行为正确性、性能和产品效果三类：

| 编号 | 标准 | 文档中的限定 |
|---|---|---|
| SC-001 | 从输入问题到首个诊断结论不超过 2 分钟 | 设备可达时 |
| SC-002 | 常见可自动修复故障成功率不低于 70% | **首期不做量化验收**，先手动验证可行性，故障清单和统计口径后补 |
| SC-003 | 对不支持设备 100% 明确拒识 | 不误诊、不误操作 |
| SC-004 | 无法唯一定位时 100% 先澄清 | 确定目标后才能操作 |
| SC-005 | 无法自动修复时 100% 提供可执行下一步 | 人工步骤或售后信息 |
| SC-006 | 新设备类型可在 1 个工作日内接入 | 不修改核心流程 |
| SC-007 | 90% 用户无需人工客服介入即可完成会话 | 正确引导至人工步骤或售后也计入完成 |
| SC-008 | 未认证访问 100% 返回 401，普通用户访问管理接口 100% 返回 403 | 访问他人设备或对话全部拒绝 |
| SC-009 | 有效、可发现、未绑定 SN 添加成功率 100% | 非法、重复、不可发现或查询失败时新增记录数为 0 |

计划另外提出单实例支持 **50 个并发会话**、设备发现查询默认 **10 秒超时**；这些属于技术计划指标，不能把它们说成已经完成压测的结果。

测试采用分层验证：单元测试覆盖规则、状态机、认证、协议解析和绑定服务；契约测试覆盖认证、请求响应、错误码及 SSE；集成测试使用真实 MySQL、Redis 和真实 `deviceSimulator`。

LLM、售后等外部服务在测试中隔离处理；设备端到端路径必须连接真实模拟器，先在模拟器创建设备、取得 SN，再调用 AutoSense 绑定。上游超时、5xx 和畸形响应等异常放在隔离客户端测试中构造，避免破坏共享模拟器环境。

当前 [tasks.md](../specs/001-iot-auto-diagnosis/tasks.md) 已改为“按 SN 绑定已有模拟器设备”的**增量任务清单**，不是全部功能的原始任务总表。它包含 26 项任务，全部标记完成，覆盖模型迁移、协议和错误映射、绑定流程、诊断回归、跨用户唯一性、并发冲突、人工指引回归及文档验证。
