# Feature Specification: 公共基础与统一意图计划器

**Feature Branch**: `002-assistant-foundation`

**Created**: 2026-09-07

**Status**: Implemented — 2026-09-15的[83项新任务](tasks.md)全部完成，LangGraph4j与五类持久数据已接入，旧编排已删除。当前设计见[plan](plan.md)，本期验收与FR/SC覆盖见[validation-langgraph](validation-langgraph.md)；旧59项任务及旧版验证仅作档案。实际部署仍须显式执行数据库迁移及配置外部模型。2026-09-20 随 004 新增的启动在线状态免确认规则仅完成规格同步，尚待规划与实施，不计入上述完成记录。

**Input**: 复用当前用户控制、设备管理、基础 DTO、鉴权、会话与流式响应；基于 LangChain4j AI Service 的 Intent Router 扩展为意图计划器，为四类能力生成单步或多步计划。公共基础负责步骤执行、用户确认、超时重试、幂等、过程记录、多轮记忆与检查点恢复。

**Feature Map**: [五个 feature 的范围、依赖与迁移映射](../README.md)。本 feature 负责公共基础，不负责四项能力的业务实现。

## Clarifications

### Session 2026-09-07

- 本次拆分按用户确认的五个 feature 执行；原有用户管理、SN 绑定和会话行为作为兼容基线。AI Service 重写是明确要求，不将已有底层模型调用视为已完成重写。
- 诊断只生成待确认控制请求；所有设备状态变更由安全设备控制 feature 统一处理。路由分类和模型输出均不构成操作授权。

### Session 2026-09-15

- Q: 本期的多步意图计划需要支持哪一种执行方式？ → A: 有序多步与条件分支；步骤可以引用前序结果作为参数，但不自动循环或增删步骤。需要新增步骤时重新生成计划。
- Q: 用户确认某个设备查询或控制步骤后，该步骤超时重试或中断恢复时，是否需要再次确认？ → A: 同一步骤的设备、操作和参数未变且确认有效时，重试或恢复可复用确认；内容变更、确认过期或新步骤需重新确认。每次实际请求仍须重新校验权限和幂等条件。
- Q: 当某个步骤明确报错、被拒绝执行，或超时重试仍未成功时，剩余计划应如何处理？ → A: 停止整个计划，保留已完成结果并报告失败原因；剩余步骤不执行。
- Q: 步骤超时后，在确认仍有效且能够保证幂等的前提下，应由系统自动重试，还是等待用户手动触发重试？ → A: 系统在配置的次数上限内自动重试，并展示重试状态；次数耗尽后停止计划。具体次数和间隔在计划阶段配置。
- Q: 服务重启后，已通过持久化检查点保存、尚未终止的计划，应由用户请求继续，还是由系统自动恢复执行？ → A: 重启后保留计划及结果，等待用户明确请求继续，再从检查点恢复执行。恢复请求不替代设备操作确认，原确认仍按有效期和参数匹配规则处理。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在同一个对话入口使用四类能力 (Priority: P1)

用户在同一对话中咨询知识、查询本人设备、描述故障或提出控制请求，系统将本轮目标转换为有序执行计划；每一步属于四类能力之一，支持引用前序结果与条件分支，模糊输入先澄清。

**Why this priority**: 统一入口和正确分流是四项能力共享的前置条件。

**Independent Test**: 对公共入口输入四类明确请求、复合请求与模糊请求，用模拟能力的接收记录验证步骤顺序、条件分支、参数引用和确认等待，无需实现各能力内部业务，也无需向真实设备下发命令。

**Acceptance Scenarios**:

1. **Given** 用户已登录，**When** 分别输入“什么是色温”“我的客厅灯现在亮度多少”“客厅灯为什么不亮”“把客厅灯亮度调到 80”，**Then** 分别进入知识咨询、设备查询、故障诊断、安全控制，诊断与控制不得合并为一个意图。
2. **Given** 无可用上下文，**When** 用户输入“帮我处理一下”，**Then** 系统追问具体目标，不读取或修改任何设备。
3. **Given** 同一会话上一轮已结束，**When** 用户提出另一类新问题，**Then** 重新生成本轮计划；最近 20 条历史消息可用于理解指代，旧结论或旧确认不得复用为本轮授权。
4. **Given** 模型返回未知步骤种类、计划结构不合法或调用失败，**When** 本轮计划无法生成，**Then** 分别进入澄清或明确的服务失败响应，不默认进入控制流程。
5. **Given** 用户请求“查询亮度，低于 30 就调到 80”且目标明确，**When** 生成计划，**Then** 包含设备查询与有条件执行的控制步骤；查询先等待用户确认，条件满足后控制步骤也须取得用户确认，条件描述不构成授权。
6. **Given** 计划的查询步骤已成功，**When** 后续条件不满足，**Then** 将相应步骤标记为跳过并说明原因，不发送该步骤的设备请求；条件满足时可将前序结果用于后续步骤参数。
7. **Given** 计划正在执行，**When** 发现目标需要原计划之外的步骤，**Then** 不自行增删步骤或循环执行，说明需要重新生成计划；新计划不继承旧设备操作的授权。
8. **Given** 故障分析需要设备状态作为证据，**When** 生成和执行计划，**Then** 将设备查询与诊断拆为独立步骤；诊断只进行知识检索和分析，需要控制时另设控制步骤。

### User Story 2 - 继续使用已有账号与本人设备 (Priority: P1)

用户沿用已有注册、登录、注销、个人信息与设备添加/列表能力；管理员沿用已有用户管理能力。

**Why this priority**: 拆分需要保持已有用户数据与权限边界，避免重复建设基础功能。

**Independent Test**: 回归已有账号、令牌、管理员管理和 SN 绑定场景，验证原有用户与设备记录仍可使用。

**Acceptance Scenarios**:

1. **Given** 用户提交有效注册资料，**When** 注册、登录、查看本人信息并注销，**Then** 操作依次成功，响应不含密码，注销后的令牌无法继续访问。
2. **Given** 用户未登录、令牌失效或已被禁用，**When** 访问受保护能力，**Then** 拒绝访问；普通用户访问管理功能也被拒绝。禁用后再启用不会恢复已撤销的旧令牌。
3. **Given** 管理员已登录，**When** 分页、按账号或昵称搜索用户并禁用/启用用户，**Then** 保持原有能力；管理员同样无权访问他人的设备或对话。
4. **Given** 外部设备服务已存在可发现且未绑定的设备，**When** 用户提交有效 SN 和显示名称，**Then** 绑定到本人名下，使用用户显示名称并保存稳定元数据；平台不代建设备。
5. **Given** SN 已绑定、无效、不可发现或查询失败，**When** 请求添加，**Then** 区分绑定冲突、格式错误、未找到与服务不可用，新增记录为零且不泄露其他用户归属。
6. **Given** 可发现设备的型号尚不支持诊断，**When** 绑定并查看列表，**Then** 允许绑定、展示元数据和支持情况；绑定成功不代表已支持诊断或控制。

### User Story 3 - 保持会话与公共响应一致 (Priority: P1)

调用方继续使用已有会话和流式响应方式，用户能查看历史并继续提问。

**Why this priority**: 四项能力需要共享可追溯的对话上下文和可恢复的交互方式。

**Independent Test**: 在同一会话切换能力、等待输入、结束并重新提问，验证历史、流关闭和断线补查行为。

**Acceptance Scenarios**:

1. **Given** 正在处理本轮消息，**When** 有用户可见的回答或状态变化，**Then** 通过既有文本、状态、等待输入、结论和错误事件语义返回，并暴露当前步骤及其状态；步骤完成后输出结果，失败时输出失败原因；提示词和内部推理不作为回答泄露。
2. **Given** 本轮进入等待输入或终态，**When** 处理结束，**Then** 关闭本次流；断线不补发历史事件，用户可补查会话状态和已保存消息。
3. **Given** 已有历史会话，**When** 查看列表或继续对话，**Then** 只可访问本人记录，长期保留历史；并发提交同一会话消息不会重复写入当前输入或串用其他用户上下文。
4. **Given** 合法的模型配置发生替换，**When** 启动并处理同一组路由请求，**Then** 使用所配置的模型且保持输出契约；无效配置明确报错，真实模式不得静默切换为模拟成功。
5. **Given** 本轮已生成并执行步骤，**When** 查询本人执行记录，**Then** 可关联用户输入、系统输出和各步骤的操作种类、结果及失败原因；其他用户不可访问。
6. **Given** 同一步骤被重复提交或从检查点恢复，**When** 该步骤已有成功结果，**Then** 复用已保存结果，不重复产生业务效果；结果尚不确定时不得将其直接当作未执行重新发送设备控制。
7. **Given** 步骤进入人工确认等待、发生尚未耗尽重试机会的超时或执行昂贵操作，**When** 中断后恢复处理，**Then** 能恢复相应步骤、已有结果和确认状态，不将未确认步骤视为已授权，也不重做已有成功结果的昂贵步骤；因明确报错、拒绝或重试耗尽而停止的计划不得借恢复继续执行。
8. **Given** 设备步骤已获用户确认且设备、操作和参数均未改变，**When** 超时重试或中断后恢复且确认仍有效，**Then** 复用该步骤的确认，不重复询问；每次实际请求仍重新校验身份、归属、权限、参数和幂等条件，校验不通过时不得执行。
9. **Given** 设备步骤准备重试或恢复，**When** 设备、操作或参数发生变化、确认已过期，或即将执行新步骤，**Then** 不复用原确认，先向用户展示本次具体操作并等待重新确认；同意另一操作或另一轮请求不构成本次授权。
10. **Given** 计划已有成功步骤且仍有未执行步骤，**When** 当前步骤明确报错、被拒绝执行或超时重试耗尽，**Then** 停止整个计划，保留成功结果并输出当前步骤失败原因及计划停止原因；所有剩余步骤均标记为因计划停止而未执行，包括与失败步骤无依赖关系的步骤。
11. **Given** 计划已因步骤失败、拒绝或重试耗尽而停止，**When** 重复提交确认、恢复请求或读取检查点，**Then** 保持计划停止状态，不重试该失败步骤，不执行剩余步骤，不重做或自动撤销已完成操作；仍可查询已保存结果和停止原因。
12. **Given** 步骤请求超时且仍有重试机会，**When** 该步骤能够保证幂等且设备操作的确认和权限校验仍有效，**Then** 系统按配置间隔自动重试，无需用户手动触发，并对外展示当前重试状态及次数；成功后继续计划，次数耗尽仍未成功则停止整个计划。
13. **Given** 步骤已经消耗部分重试次数，**When** 中断恢复或下层调用组件参与重试，**Then** 同一逻辑步骤的总重试次数仍受同一配置上限约束，不因恢复或多层重试而增加预算；明确报错或拒绝执行时立即停止计划，不消耗剩余次数继续尝试。
14. **Given** 未终止计划已有持久化检查点，**When** 服务进程重启且用户尚未明确请求继续，**Then** 保留计划、步骤结果、确认状态和已消耗的重试次数，对外显示等待恢复；启动或查询历史本身不触发步骤执行。
15. **Given** 服务重启后本人请求继续一个未终止计划，**When** 校验身份和计划归属通过，**Then** 从检查点恢复原计划，不重新生成计划或重做已成功步骤；设备操作仍校验原确认的有效期、设备、操作和参数，缺少有效确认时等待重新确认，当前权限被拒绝时停止计划。
16. **Given** 同一未终止计划等待恢复，**When** 用户重复或并发提交继续请求，**Then** 同一逻辑步骤不会被并行重复执行；他人请求恢复被拒绝，已完成或已终止计划只返回已有状态和结果。
17. **Given** 步骤的请求超时时间达到配置的昂贵步骤阈值，**When** 该步骤成功结果已保存且服务随后重启，**Then** 用户请求继续后复用该结果，不重新调用该昂贵能力；检查点缺失或不可用时明确报告不能恢复，不从头重放计划。
18. **Given** LangGraph4j移植已经完成，**When** 启动应用并使用新建、续聊、确认、恢复及历史查询接口，**Then** 不再依赖SessionOrchestrator、旧状态机或旧上下文续接；源代码和Bean中不存在旧编排实现，图执行失败也不回退旧链，既有历史和共享业务能力仍可用。

### Edge Cases

- 明确与四项能力无关的请求：说明服务范围；信息不足时澄清，不强行选取设备意图。
- 一个请求包含多个意图或多台设备的操作：拆为有序步骤，可按前序结果选择条件分支；每个设备查询或控制步骤均须经过用户确认，不因同属一个计划而自动获得授权。
- 已有待确认操作时收到新问题：安全控制 feature 决定旧请求取消或失效；新的普通消息不得隐式确认旧操作。
- 登录过期、账号禁用、会话不属于本人、模型异常和断线均须给出明确结果，不能导致未经确认的设备查询或控制。
- SN 并发重复绑定必须保持全局唯一；运行状态不得因列表缓存而被当作权威实时状态。
- 条件引用的前序结果缺失或不可用时，不得将条件默认为成立；明确暴露当前步骤无法执行的原因。
- 超时不等于明确失败，也不证明设备未执行；允许重试的同时必须保持步骤幂等。明确报错或拒绝执行的步骤不得重试。
- 重试或恢复时只可复用同一步骤仍有效且与设备、操作、参数完全匹配的确认；确认过期或操作内容改变时必须重新确认，权限被撤销时即使确认未过期也不得执行。
- 单一步骤明确报错、被拒绝执行或超时重试耗尽时，整个计划停止，无依赖的剩余步骤也不继续；条件不满足导致的正常跳过不属于失败，不触发此停止规则。停止计划不等于回滚已完成操作，也不证明超时设备操作未生效，已有结果和不确定状态均须保留并说明。
- 超时后的自动重试不能绕过人工确认、当前权限或幂等保障：确认过期须先重新确认，权限被拒绝须停止计划，无法保证幂等时不得自动重发设备控制。重试次数不得因恢复或下层组件的独立重试而被重置或突破。
- 服务重启后，查询会话、读取检查点或普通新问题不构成继续原计划的请求；只有本人明确请求继续才启动恢复。缺失或不可用的检查点不得退化为从头重放，已完成或已终止的计划不得恢复执行。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的自然语言会话入口，在每轮新工作流的意图路由／意图规划前，按 [004 FR-014–016](../004-user-device-query/spec.md) 加载当前用户全部已绑定设备的基础信息，包含设备 ID、名称、SN 号、设备类型、设备型号和在线状态，作为计划制定的依据之一。意图计划器 MUST 结合该上下文、用户请求及已有对话上下文，将明确请求转换为单步或有序多步执行计划；每一步的操作种类 MUST 为知识咨询、设备查询、故障诊断或设备控制之一。基础信息读取是规划前固定步骤；已加载信息足够回答时走直接回答，不生成DEVICE_QUERY/list/metadata，不要求设备查询确认；已有事实也须传给最终回答服务。初始化含离线设备，无设备时传入空集合，在线状态缺失按离线处理并保留原因；同一工作流继续或恢复复用已保存的基础信息。
- **FR-002**: 系统 MUST 区分四种业务意图及无法确定的结果；原有合并诊断/控制的 `DEVICE_ACTION` 语义 MUST 被拆开。型号知识归知识咨询，明确的售后查询归诊断 feature 的售后引导分支，均不得因此触发设备写操作。
- **FR-003**: 系统 MUST 使用本轮输入和本人会话上下文生成计划；无法确定目标或必要条件时追问；模型失败时报告失败。计划 MUST 支持有序多步、条件分支和引用前序结果作为后续参数；执行中 MUST NOT 自动循环或增删步骤，需要新增步骤时 MUST 重新生成计划。条件不满足的步骤 MUST 标记为跳过并说明原因，条件依赖的结果不可用时 MUST NOT 默认执行。
- **FR-004**: 意图计划器与 AI Config MUST 基于 LangChain4j AI Service 实现，提供有明确结构化输出契约的计划与分析能力，以及用户可见的回答能力。复用统一模型配置，并通过对应的专用工厂创建 AI Service，不恢复已移除的统一 AiServiceFactory；只声明未被实际调用的 AI Service 接口不满足要求。
- **FR-005**: AI 配置 MUST 外部化管理模型连接、模型选择及调用参数，复用现有配置入口；四项能力 MUST 复用统一配置与创建机制。真实模式 MUST NOT 静默模拟成功；明确测试模式可继续使用既有模拟 AI。
- **FR-006**: 计划与 AI 输出 MUST 仅作为候选业务输入；身份、设备归属、权限和可执行性 MUST 由服务端确定。故障诊断 MUST 作为特化的知识检索与分析步骤，所需设备查询和设备控制 MUST 由独立步骤完成；AI MUST NOT 绕过权限、校验、确认和审计直接访问或控制设备。
- **FR-007**: 系统 MUST 复用已有用户、设备、会话、消息和公共 DTO/响应契约，保留现有数据；仅为拆分所需补充字段或职责归位，MUST NOT 另建重复的用户或设备管理体系。
- **FR-008**: 系统 MUST 保持注册、登录、当前用户信息、注销及管理员列表/搜索/禁用/启用；新注册用户只能为普通用户。账号为 4–32 位字母、数字或下划线。注册密码须满足现有 8–64 位长度校验，同时包含英文字母和数字，且 UTF-8 编码后不得超过 72 字节；两次密码一致。超出限制 MUST 返回明确的参数错误，不得通过截断密码使其通过校验。昵称缺省取账号；密码安全存储且不出现在响应或日志中。
- **FR-009**: 系统 MUST 要求登录后使用四项能力，只允许访问本人设备和会话；普通用户不可访问管理功能。注销、过期或禁用后的令牌 MUST 失效，启用账号不得复活旧令牌；本地开发身份机制仅可通过显式测试/开发开关启用，生产关闭。
- **FR-010**: 系统 MUST 保持按 SN 绑定已有可发现设备的行为、SN 全局唯一和用户显示名称优先；保存外部设备 ID、SN、类型/型号编码与 ID、原始名称、显示名称和归属，MUST NOT 将设备运行状态或外部时间戳作为绑定元数据持久化。不支持诊断/控制的型号仍允许绑定。
- **FR-011**: 绑定失败 MUST 不新增或覆盖记录；非法 SN、未找到、重复绑定、外部服务不可用须分别给出原有明确错误语义，重复绑定错误不得泄露所有者。
- **FR-012**: 对话与用户可见消息 MUST 长期保留，支持本人历史列表、详情、新建与继续；ChatMemory MUST 服务多轮会话，模型使用最近 20 条历史窗口加当前输入一次；结束后新问题重新生成计划，各用户、会话与处理轮次 MUST 隔离。历史消息和 ChatMemory MUST NOT 作为设备授权或步骤恢复状态的权威依据。
- **FR-013**: 系统 MUST 保持现有会话 POST 流式响应及 GET 补查契约：用户可见文本逐步返回，等待输入或终态关闭本轮流，断线不补发；公共错误与状态事件在四项能力中语义一致。Controller MUST 对外暴露当前执行步骤的标识、操作种类和状态，步骤完成后输出该步骤结果，失败时输出失败原因；上述结果 MUST 支持断线后的本人补查，不暴露内部推理。
- **FR-014**: 系统 MUST 持久化并关联用户输入、系统输出、执行计划、每个步骤的操作种类、操作结果及失败原因，保留澄清和关键状态的追溯关系，供本人历史查询和受权限控制的设计分析使用。业务记录与运行日志 MUST 分离，运行日志不得记录完整对话或提示词；任何记录 MUST NOT 包含密码、令牌或模型密钥。

- **FR-015**: 公共基础 MUST 复用已有设备定位、归属检查、客户端/适配契约与设备互斥机制，供各能力调用；各能力负责本轮业务校验及占用生命周期，MUST NOT 为拆分复制平行的设备接入或锁实现。
- **FR-016**: 除 [004 FR-014/FR-016](../004-user-device-query/spec.md) 定义的意图规划前设备基础信息初始化外，设备查询及设备请求 MUST 在执行前取得用户确认。该例外允许自动加载本人设备已有基础信息（含ID、名称、SN、类型、型号、已有描述/固件）及外部服务在线状态，供意图计划器和基于已有事实的直接回答使用；仍须校验身份、归属和权限，允许使用 POST /device/{sn}/get 探测在线状态，但只保留 properties.online；其他属性丢弃，不包含业务运行属性查询及 SET、ACTION，也不构成后续操作授权。需确认的操作 MUST 将确认绑定当前用户、计划、逻辑步骤及已明确的设备、操作和参数；004运行属性查询明确授权完整GET快照，展示范围并绑定能力hash。同一步骤超时重试或中断恢复时，若上述内容未变且确认仍有效，MAY 复用该确认而不重复询问；设备、操作、参数、完整GET范围或能力hash变化、确认过期或执行新步骤时 MUST 重新展示操作并取得确认。每次实际请求 MUST 重新校验身份、设备归属、权限、参数及幂等条件，确认 MUST NOT 替代这些校验。计划中的条件描述、其他步骤或轮次的历史同意、普通消息 MUST NOT 被视为当前操作的确认。
- **FR-017**: 每个步骤在请求超时、仍有重试预算且能够保证幂等时，系统 MUST 按配置的间隔自动重试，无需用户手动触发；设备操作还 MUST 满足 FR-016 的确认与权限校验。重试次数 MUST 有限且可配置，上限按同一逻辑步骤的首次尝试之后的额外尝试计数，下层调用组件的重试也 MUST 纳入该上限。系统 MUST 区分超时、明确失败和拒绝执行，保存尝试结果，并对外展示重试状态、已重试次数和配置上限；明确报错或拒绝执行时 MUST NOT 重试，重试耗尽仍未成功时 MUST 按 FR-020 停止整个计划。具体次数和间隔在 plan 中确定。
- **FR-018**: 每个逻辑步骤 MUST 有稳定标识，重复提交、超时重试和检查点恢复 MUST 保持幂等，不重复产生业务效果；已成功步骤 MUST 复用已保存结果。设备控制结果不确定时 MUST 保留不确定状态，不得仅因超时就重新产生一次控制效果。
- **FR-019**: CheckPoint（检查点）MUST 持久化并在服务进程重启后可用，覆盖人工确认、失败恢复和昂贵步骤恢复场景，保留计划、当前步骤、已有步骤结果、确认状态和已消耗的重试次数；恢复 MUST 校验当前访问权限和授权有效性。失败恢复 MUST 遵守 FR-017 和 FR-020，不得重置重试次数或重新执行已终止计划。昂贵步骤 MUST 根据期望耗时识别，期望耗时以该步骤配置的请求超时时间为依据，达到配置阈值的步骤视为昂贵步骤；等待用户确认的耗时不属于外部请求耗时。恢复 MUST 复用已保存的成功结果；检查点缺失或不可用时 MUST 明确报告无法恢复，MUST NOT 从头重放计划。
- **FR-020**: 任一计划步骤明确报错、被拒绝执行或超时重试耗尽后，系统 MUST 停止整个计划，保留已完成结果，并对外报告失败步骤、失败原因和计划停止原因。所有剩余步骤 MUST 标记为因计划停止而未执行，即使与失败步骤无依赖关系也不得继续；MUST NOT 通过检查点恢复或重复确认重启该计划。正常条件跳过不构成失败。停止计划 MUST NOT 自动撤销已完成操作，设备执行结果不确定时 MUST 如实保留并披露该状态。004 FR-014/FR-015 的启动在线状态加载属于初始化，其外部获取失败不作为计划步骤失败：保留已获取状态，缺失设备按离线处理并记录原因，工作流继续；该例外不放宽后续步骤的必要条件与失败停止规则。
- **FR-021**: 服务重启后，系统 MUST 保留未终止计划及已保存结果并对外暴露等待恢复状态，MUST NOT 自动执行计划步骤；只有当前用户明确请求继续本人计划后，才可从持久化检查点恢复。恢复请求 MUST NOT 替代 FR-016 的设备操作确认，原确认仍须校验有效期及设备、操作和参数匹配情况；无有效确认时 MUST 等待重新确认。重复或并发恢复请求 MUST 遵守步骤幂等约束；已完成或已终止的计划 MUST 保持原状态，不恢复执行。服务未重启时，满足 FR-017 条件的超时仍按既定规则自动重试。

- **FR-022**: LangGraph4j移植完成后，系统 MUST 删除SessionOrchestrator及旧编排专属的状态机、上下文续接、能力分发和回调驱动流程，不得保留精简门面或运行回退链。迁移 MUST 保留所需的鉴权、事务、历史查询、并发保护、知识和设备单操作能力，并解除它们对旧编排类型的依赖；当前设计和测试 MUST 同步到新图，旧设计只可作为明确标记的历史档案保留。

- **FR-023**: 对话流程 MUST 明确区分conversation、chat_message、workflow_execution、command_execution、audit_event五类逻辑持久数据，优先复用已有表、标识和历史记录。会话承载多轮消息与执行，命令执行记录独立保存设备控制的幂等身份及结果，审计追加记录操作事实；同一命令的重试/恢复不得生成新的逻辑命令或覆盖审计历史。步骤、确认和检查点作为工作流内部数据保留，具体物理映射在plan/data-model中定义。

### Key Entities

- **用户与设备绑定**: 复用现有账号、角色、SN 唯一性、设备归属和稳定元数据。
- **对话与处理轮次**: 对话长期保留，一轮对应一次用户请求的处理；待确认操作与当前轮次关联，不等于整个对话永久授权。
- **意图执行计划与步骤**: 一轮目标对应单步或有序多步计划；每步具有稳定标识、操作种类、目标及参数、前序结果引用、可选执行条件、状态和结果。计划保留整体状态及停止原因，区分条件不满足而跳过与计划停止而未执行。计划是候选业务输入，不是已验证的设备身份或操作权限。
- **规划设备上下文**: 意图规划前准备的本人全部设备基础信息集合，包含 ID、名称、SN 号、设备类型、型号和在线状态，保留状态来源及获取时间；按工作流保存与复用，不能替代后续权限校验或用户确认，具体来源和失败处理遵循004；可用于基础事实直接回答，不作为设备运行属性证据。
- **步骤执行记录与确认**: 同一逻辑步骤的执行尝试、超时、失败及最终结果可追溯；确认记录关联用户、计划、逻辑步骤及已明确的设备、操作和参数，并保留确认状态与有效期。同一步骤重试或恢复可按 FR-016 复用仍有效的确认，不等于整个计划或会话永久授权。
- **检查点**: 持久化且可跨进程重启读取的计划与步骤状态、已完成结果、人工确认状态及已消耗的重试次数，覆盖人工等待、失败及昂贵步骤恢复；重启后原计划等待本人明确请求继续，与用于理解多轮消息的 ChatMemory 职责不同。
- **公共请求/响应及消息**: 复用原有 DTO、展示对象和事件类型；新增能力使用同一公共交互契约。
- **命令执行与审计事件**: 命令执行表示控制步骤的同一逻辑命令，跨尝试保持身份并记录效果确定性；追加审计记录各类步骤、确认、恢复和命令尝试的事实。命令状态、审计事件和面向客户端的事件各自独立，不能以审计写入成功宣称设备命令成功。
- **AI 能力配置**: 配置统一的模型接入、调用参数与能力创建方式，敏感值从环境注入。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 验收样例中四类明确请求全部生成正确步骤；复合请求的顺序、条件分支和前序结果引用全部符合预期，无自动循环或增删步骤；模糊、非法计划及未经确认的设备操作样例均不产生设备调用。
- **SC-002**: 已有用户、管理员、SN 绑定和历史会话回归场景全部通过，原有有效用户与绑定记录继续可用。
- **SC-003**: 未登录/失效身份、越权设备/会话及普通用户管理请求的拒绝率为 100%；响应或日志中的凭据泄露为零。
- **SC-004**: 会话跨能力、跨轮次、等待、终态和断线补查场景全部保持正确关联；重复保存当前消息及用户间上下文串用为零。
- **SC-005**: 有效配置切换与无效配置失败场景均可验证；四项能力接入公共入口不需要重建用户、设备或会话体系。
- **SC-006**: 所有步骤验收场景均可查询当前步骤及状态，并取得完成结果或失败原因；每一步均能追溯所属用户输入与系统输出。
- **SC-007**: 重复提交、超时重试和检查点恢复验收场景中，重复业务效果为零；明确报错或拒绝执行后的步骤重试次数为零；已成功的昂贵步骤恢复后重复执行次数为零。满足自动重试条件的超时场景无需用户手动触发即可重试，重试状态和次数均可查询；包含中断恢复和下层重试的全部场景中，每个逻辑步骤的额外尝试总数不得超过配置上限。
- **SC-008**: 需确认的同一步骤操作内容未变且确认有效的重试/恢复场景中，重复确认提示次数为零；设备、操作、参数变化或确认过期、新步骤场景中，取得新确认前的设备请求次数为零；当前权限校验不通过的设备请求次数为零。FR-016 的启动在线状态例外不弹出确认，其仅允许在线探测 POST，其他业务设备 GET、SET、ACTION 调用次数为零，不能免除后续步骤确认。
- **SC-009**: 明确报错、拒绝执行及超时重试耗尽的验收场景中，后续步骤执行次数为零，已完成结果保留率为 100%，失败步骤及停止原因均可查询；重复确认或恢复请求导致已终止计划再次执行的次数为零。
- **SC-010**: 服务重启验收场景中，本人明确请求继续前的步骤执行次数为零；恢复后已保存结果与已消耗重试次数的保留率为 100%，已成功昂贵步骤的重复调用次数为零；无有效确认的设备请求、他人恢复及重复恢复导致的重复业务效果均为零。检查点不可用时不得从头重放，已完成或已终止计划的恢复执行次数为零。

- **SC-011**: 移植完成的生产源码、Bean装配与当前测试对旧编排类的依赖数为零；新建、消息、确认、恢复与取消均使用新图；旧API外形和历史读取回归通过，新图失败时旧链调用次数为零。当前架构说明不得将旧编排列为最终组件。

- **SC-012**: 存量升级和新建库验收中，五类逻辑数据均可按会话/工作流追溯；原会话ID、消息正文和动作审计保留率为100%，无重复会话或审计副本。控制重试/恢复复用同一命令身份，各次尝试审计可查；命令结果已提交但检查点失败的恢复场景中，重复控制效果和重复最终消息均为零。

## Assumptions

- 依赖与目录约束遵循[章程](../../.specify/memory/constitution.md)：AI Service 创建工厂在 `ai/factory`，AI 结构化输出在 `ai/model`，AI 分类枚举在 `ai/model/enums`；业务枚举在 `domain/enums`，DTO 在 `domain/dto`，VO 在 `domain/vo`，全局常量在 `constant`，工具在 `utils`。具体接口、类迁移和装配方式在本 feature 的 plan 中定义。
- 当前可复用代码入口为 `controller`、`service/user`、`core/security`、`core/device`、`core/session`、`domain/dto`、`domain/message`；这是复用依据，不表示全部满足新验收要求。
- 当前 `config/LangChain4jConfig`、`core/routing/IntentClassifier` 和 `domain/enums/Intent` 是重写/调整对象；已有底层模型调用与手动解析不视为完成 AI Service 方案。
- 仅扩展现有后端 API 能力；不要求重做仓库已有前端，不增加角色修改、他人密码重置、设备代创建、自动循环、执行中自动增删步骤或跨会话长期偏好记忆。
- 四能力内部业务分别在其他feature交付；本feature负责公共图及已有能力迁接，不重建全部业务。公共plan、契约与新tasks已同步，其他feature按实际缺口更新；骨架可用模拟能力独立验收，但真实迁接及完整切换不能以stub验收替代。
- 当前 plan 已定义步骤请求超时、重试上限与间隔、确认有效期、昂贵步骤阈值及检查点/恢复接口。现有设备接口缺少远端幂等键及按操作 ID 核对结果的能力，因此未知写结果禁止重发；后续实现验证不得放宽确认、停止与禁止重复业务效果规则。
- 用户明确指定 LangGraph4j 重写编排，Controller 从 graph stream 的 State.OutputContext 投影 WorkflowEvent 再发送 SSE，不能直接暴露内部 AgentState。State 保留 RequestContext、PlanContext、WorkflowContext、DeviceContext、DiagnosisContext、ControlContext、RetryContext、AuditContext、OutputContext 和 messages；字段与更新权威见 data-model.md。
- 用户指定 MainGraph 正常路径为 IntentPlanner → PlanValidator → PlanRouter → 知识节点或 Query/Diagnosis/Control 子图 → CompleteStep → 下一步或 ResponseAggregator；无效计划进入 Reject。失败停止和人工中断规则仍适用，不将失败步骤标记为完成。
- graph 目录已确认位于 src/main/java/com/chh/autosense/graph/，与 controller、core 同级，包含 MainGraphFactory、state、node、subgraph 三个工厂及 checkpoint；AI Service 工厂仍位于 ai/factory。requestId 作为检查点 threadId，骨架先使用明确标识的 stub 跑通整体流程。

## 2026-09-09 意图识别扩展

- 每个 KNOWLEDGE 步骤 MUST 包含 `requiresKnowledgeBase` 布尔判断：无需产品资料的通用常识为 false；型号规格、产品文档、专有功能等依赖知识库的问题为 true；无法确认属于常识时选择 true。
- DEVICE_QUERY MUST 包括需要读取本人具体设备参数后才能解释、比较、估算或提出建议的问题；不只限于直接列出参数。仅询问某型号公开规格仍属于 KNOWLEDGE 且需要知识库。
- 只读分析不构成 CONTROL；直接状态变更仍走确定性的控制步骤。故障原因分析属于 DIAGNOSIS，是特化的知识检索与分析步骤；需要设备证据或控制时分别安排独立步骤。
- `requiresKnowledgeBase` 仅用于内部计划及能力请求，非 KNOWLEDGE 步骤必须为 null；知识步骤缺失该判断视为非法计划并澄清。意图计划器不执行知识检索或设备访问。
- 意图计划器消费规划前已加载的本人全部设备基础信息；加载顺序和六个必要字段遵循 FR-001，完整性、离线设备保留及实际用于规划的验收遵循 004 SC-010。


### 2026-09-23 会话删除修订

会话删除不得仅因工作流未终止而永久拒绝。本人会话在没有有效执行租约、没有执行中或结果不明的设备命令时可删除，包含中断、等待确认和等待恢复；无需先恢复执行。有效执行、旧版未完成 processing 标记及未确定命令继续保护，界面显示具体拒绝原因。列表状态依据最新工作流投影，旧会话无工作流时使用原状态。删除后清理关联数据，旧执行者不得重新写入或恢复被删任务。
