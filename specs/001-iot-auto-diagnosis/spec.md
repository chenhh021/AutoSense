# Feature Specification: IoT 设备自动诊断与修复

**Feature Branch**: `001-iot-auto-diagnosis`

**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "根据用户输入，自动检测IoT设备和网络设备可能存在的问题，尝试修复；目前支持设备种类：路由器、空调、智能灯泡，功能列表待添加；支持后续扩招到更多种类的设备。运行逻辑：1.用户输入问题 2.分析用户问题，得到用户问题的关键点属性：设备类型，问题表现（复现方式）3.定位到对应设备 4.判断设备是否在支持范围内 5.向设备请求基础诊断信息，结合用户问题找到设备问题 6.根据问题通过RAG搜索解决方式，尝试修复 7.修复执行完毕后，再次获取设备基础诊断信息，给出结论 8.当发现无法自动修复时：根据情况采取不同方式应对用户：（1）明确知道修复步骤时，告知无法修复的原因与具体操作步骤（2）操作步骤不明时，帮客户查询附近售后的地址和联系方式"

## Clarifications

### Session 2026-08-21

- Q: 谁能对一台设备发起诊断和修复——系统如何确认用户有权操作这台设备？ → A: 账号+设备绑定：用户登录后仅能操作名下设备，越权请求一律拒绝
- Q: 同一台设备正在执行修复时，又收到针对它的新请求，系统应该怎么处理？ → A: 设备级互斥：同设备仅一个进行中会话，新请求提示"该设备正在处理中，请稍后"
- Q: 修复操作执行到一半失败（例如部分配置已修改但操作报错）时，系统应该怎么做？ → A: 失败即停：停止后续动作，复检当前状态，如实告知并转人工引导
- Q: 用户通过什么入口与这个诊断修复功能交互？ → A: 仅提供 API：不做任何界面，由调用方自行实现交互
- Q: 诊断修复会话记录（含用户问题描述、诊断信息、操作日志）应保留多长时间？ → A: 90 天：兼顾追溯与隐私的折中

### Session 2026-08-22

- Q: SC-002(自动修复成功率 ≥70%)本期如何验收？ → A: 本期不作量化验证,仅通过手动场景验证可行性;故障清单与统计口径待知识库案例丰富后补充
- Q: 当前阶段设备交互 mock 如何实现? → A: 项目内硬编码 mock,所有修复操作一律返回成功;不使用独立 mock server(2026-08-27 修订:撤销,改由 deviceSimulator 独立服务替代,见下)

### Session 2026-08-22(对话记忆补强)

- Q: 对话记忆的边界是单会话内还是跨会话? → A: 新增对话保存机制:用户可选择新增对话或继续已有对话;每个对话长期保留;对话用 session id 唯一标记
- Q: 对话保留策略与 FR-013 的 90 天清理冲突,以哪个为准? → A: 全部长期保留:撤销 90 天策略,FR-013 改为不设期限
- Q: 终态对话能否直接继续提新问题? → A: 终态可继续:同一对话线程内可发起新一轮诊断(状态机增加终态→ANALYZING 回路)
- Q: 继续对话时 LLM 端能看到多少历史消息? → A: 最近 20 条消息窗口(超出部分 LLM 不可见,但仍长期留存可查)

### Session 2026-08-22(问题路由)

- Q: 路由(2)"开始操作前需要授权"的授权范围? → A: 探测(诊断信息采集)免授权,所有改变设备状态的操作一律先经用户确认(确认门从"仅中断型"扩为"全部操作")
- Q: 型号特异性问题的 RAG 标注"后续添加",本期如何响应? → A: 本期并入常识类由 LLM 直接回答;型号 RAG 知识库后续作为准确率增强接入,路由层无需改动
- Q: 网点查询"模拟生成"的数据形态? → A: 项目内固定 mock 网点列表(与设备 mock 方针一致,确定可测);后续仅替换查询实现为地图搜索工具
- Q: 意图分类无法确定路由时默认行为? → A: 追问澄清(复用 CLARIFYING/FR-002);宁可多问一轮,不得因误分类触碰设备

### Session 2026-08-27(模拟设备对接)

- Q: deviceSimulator 独立服务与此前"项目内硬编码 mock"澄清冲突,对接方式怎么定? → A: 模拟器完全替代 mock:设备交互唯一实现为 HTTP 调用 deviceSimulator(默认 localhost:8081,base-url 经 yml 配置),项目内硬编码 mock 删除
- Q: 模拟器目前仅支持智能灯泡(LITE:LA001/LB001),原三类设备范围如何收敛? → A: 暂停多类型支持:本期仅智能灯泡经模拟器接入;路由器/空调待模拟器扩展型号后接入,架构扩展约束(FR-012)不变
- Q: 模拟器无故障注入能力,诊断/修复场景怎么构造? → A: 状态值映射故障:诊断=读取设备 state,故障判定规则配置化(如 brightness 异常低/stopped→故障),修复=下发对应命令(set_brightness/start 等)恢复正常值,规则写在 yml 设备注册表
- Q: 模拟器设备无用户归属,与 FR-015 账号绑定如何衔接? → A: 本平台维护绑定：device 表记录 SN 和模拟器设备 ID，用户通过 SN 与设备名称添加设备，越权拒绝不变（2026-09-04 修订）
- Q: 原内置 mock 的固定故障场景删除后,US2"不可自动修复"分支怎么触发? → A: 规则映射不可修复结论:故障判定规则配置化支持"不可自动修复"结果(如硬件故障标志/启动失败→人工步骤或售后),确定可测,不依赖 LLM 自由判断
- Q: 模拟器为外部服务,自动化测试怎么覆盖设备交互? → A: 测试连真实模拟器:集成测试环境启动真实 deviceSimulator(如 docker-compose 引入模拟器),不经 WireMock 打桩设备路径(2026-08-27:模拟器已有外部实现,本项目不开发模拟器本体,仅从配置 url 调用)
- Q: 设备须先存在于模拟器,创建/登记职责怎么划分? → A: 2026-09-04 已修订：本平台不再代建设备；用户提交 SN 和设备名称后，后端按 SN 查询已存在的可发现设备，成功后再写入绑定记录

### Session 2026-08-27(SSE 流式推送)

- Q: SSE 流推送什么内容? → A: 文本流+状态事件:LLM 生成内容(常识回答/结论/指引)逐 token 推送,同时推送状态机关键节点事件(状态迁移/等待确认/终态结论)
- Q: SSE 通道形态? → A: POST 即 SSE 流:POST /sessions 与 POST /sessions/{id}/messages 直接返回 text/event-stream;GET /sessions/{id} 轮询端点保留(供非 SSE 客户端与断线补查),不加独立订阅端点
- Q: SSE 连接生命周期与断线处理? → A: 连接只覆盖本次 POST 的处理过程:进入等待用户态或终态时服务端主动结束流;断线不补发事件,客户端用 GET /sessions/{id} 补查当前状态

### Session 2026-08-29(用户管理)

- Q: 用户登录成功后,系统用什么凭证来维持登录状态? → A: Redis 令牌:登录生成随机 token 存 Redis(带过期),请求头 `Authorization: Bearer <token>`;注销=删除 token 立即失效
- Q: 真实登录体系上线后,dev-mode 令牌(`user-{id}`)还保留吗? → A: 保留为显式开关:`AUTH_DEV_MODE=true` 时 dev 令牌仍可用(仅测试/本地),真实 Redis 令牌始终优先解析;生产部署必须关闭
- Q: 管理员"管理其他用户"具体包含哪些操作? → A: 最小集:用户列表(分页/按账号昵称搜索)+ 禁用/启用(软删,复用 isDelete);被禁用用户令牌立即失效且不可登录;不含改角色/重置密码
- Q: 注册时账号和密码的校验规则怎么定? → A: 账号 4~32 位(字母/数字/下划线,唯一);密码 8~64 位且须同时含字母和数字;BCrypt 加密存储;昵称缺省取账号

### Session 2026-09-04

- Q: 当同一 SN 已绑定设备时，再次添加应如何处理？ → A: SN 在平台内全局唯一；无论已绑定当前用户还是其他用户，重复添加均报错
- Q: 用户输入的“设备名称”与查询接口返回的 `name` 不一致时，设备列表应使用哪个名称？ → A: 使用用户输入名称作为平台显示名称；接口返回的 `name` 仅作为模拟器原始名称
- Q: SN 查询到存在的设备，但其类型或型号当前不支持诊断时，是否仍应加入设备列表？ → A: 仍加入设备列表；发起诊断时提示该类型或型号暂不支持
- Q: 当 SN 查询因格式错误、超时或设备服务返回 5xx 失败时，应如何向调用方反馈？ → A: 区分三类结果：格式错误提示 SN 不合法，`exists: false` 提示设备不存在或不在线，超时或 5xx 提示设备服务暂不可用；均不写入设备列表
- Q: 成功添加设备后，平台应保存 SN 查询结果中的哪些信息？ → A: 保存模拟器设备 ID、SN、类型/型号编码和 ID、模拟器原始名称；不保存 `state`、`running_status` 或模拟器时间戳，运行信息按需实时查询

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自动诊断与修复闭环 (Priority: P1)

用户用自然语言描述设备问题（如"卧室空调开了不制冷"）。系统从描述中识别设备类型与
问题表现，定位到用户的对应设备，确认设备在支持范围内，随后获取该设备的基础诊断
信息，结合用户描述推断问题原因，检索匹配的解决方案并自动执行修复操作，修复完成
后再次获取诊断信息进行验证，最后向用户给出明确结论（已修复 / 未修复及原因）。

**Why this priority**: 这是产品的核心价值——让用户无需任何技术知识即可解决设备故障。
没有此闭环，其余故事均无意义。

**Independent Test**: 接入一台可模拟故障的受支持设备，输入一条典型问题描述，
端到端验证"输入问题 → 诊断 → 修复 → 复检 → 结论"全流程，即可独立交付价值。

**Acceptance Scenarios**:

1. **Given** 用户家中有一台已接入且受支持的智能灯泡，**When** 用户输入"客厅的灯
   不亮了"且故障属于可自动修复类，**Then** 系统自动完成诊断与修复，并告知用户
   "问题已修复"及修复内容，复检结果显示设备恢复正常。
2. **Given** 一台已接入的智能灯泡，**When** 用户输入"客厅灯太暗了"且诊断为可自动
   调节的状态问题，**Then** 系统经用户确认后执行调节操作并复检，向用户报告操作
   结论与复检后的设备状态。（原路由器 Wi-Fi 场景待模拟器扩展路由器型号后启用）
3. **Given** 用户名下有多台同类设备，**When** 用户描述的问题无法唯一确定目标设备，
   **Then** 系统向用户列出候选设备并要求确认后再继续诊断。
4. **Given** 用户已登录、deviceSimulator 中存在一台运行中且尚未绑定的设备，**When**
   用户提交该设备的有效 SN 和显示名称，**Then** 系统按 SN 查询设备并将其加入当前用户的
   设备列表，列表记录用户提交的显示名称以及查询返回的设备类型和型号。

---

### User Story 2 - 无法自动修复时的用户引导 (Priority: P2)

当诊断出的问题无法通过远程自动操作修复时，系统分两种情况引导用户：
(a) 若已知明确的人工修复步骤（如"需更换滤网"、"需重新插拔光纤"），系统告知
无法自动修复的原因和具体的分步操作指引；(b) 若无法确定操作步骤，系统根据用户
所在位置查询附近售后网点的地址和联系方式并提供给用户。

**Why this priority**: 保证任何诊断结论下用户都能得到可执行的下一步，避免流程
"死胡同"，直接影响用户满意度与工单转化率。

**Independent Test**: 构造两类不可自动修复的故障场景（步骤明确 / 步骤不明），
分别验证系统输出人工指引与售后网点信息，无需依赖故事 1 的自动修复能力。

**Acceptance Scenarios**:

1. **Given** 诊断结论为"空调滤网堵塞，需人工清洗"，**When** 系统判定无法远程修复，
   **Then** 用户收到无法自动修复的说明与清晰的分步人工操作指引。
2. **Given** 诊断结论无法匹配到明确的修复步骤，**When** 流程进入人工引导，
   **Then** 系统询问或使用用户位置，并返回至少一个附近售后网点的名称、地址与
   联系方式。

---

### User Story 3 - 用户账号体系与权限控制 (Priority: P1)

用户注册账号并登录后使用诊断服务：注册（账号/密码/确认密码）、登录、查看当前
登录用户信息、注销。用户分普通用户与管理员：管理员额外可管理其他用户；每个用户
拥有自己的设备列表，只能看见自己的对话。

**Why this priority**: FR-015 要求登录后使用且设备/对话按用户隔离——账号体系是
一切业务功能的前置；没有它，越权防护与"我的设备/对话"都无从落地。

**Independent Test**: 注册新账号 → 登录获得令牌 → 凭令牌访问受保护接口成功 →
注销后同一令牌失效；普通用户访问管理接口被拒，管理员可执行用户管理操作。

**Acceptance Scenarios**:

1. **Given** 一个未被占用的账号名，**When** 用户提交账号+密码+确认密码注册，
   **Then** 注册成功，随后可用该账号密码登录获得访问令牌。
2. **Given** 已注册用户，**When** 用错误密码登录，**Then** 登录被拒并提示账号
   或密码错误。
3. **Given** 已登录用户，**When** 请求当前用户信息，**Then** 返回本人账号信息
   （不含密码）。
4. **Given** 已登录用户，**When** 注销后再次用同一令牌访问，**Then** 按未登录
   处理（401）。
5. **Given** 普通用户，**When** 调用用户管理接口或访问他人设备/对话，**Then**
   一律拒绝；管理员可管理其他用户，但同样只能看见本人的设备与对话。

---

### Edge Cases

- 用户输入过于模糊（如"设备坏了"），无法提取设备类型或问题表现：系统应追问
  澄清，而不是盲目猜测。
- 用户输入涉及多台设备或一次描述多个问题：系统应拆分并逐个处理，或引导用户
  一次处理一个。
- 设备离线或诊断信息请求超时：系统应告知用户设备当前不可达，并给出检查建议
  （电源、网络连接），不得伪造诊断结果。
- 修复操作执行失败或执行后复检仍未恢复：系统应进入故事 2 的人工引导分支。
- 所有改变设备状态的操作（如调节灯泡亮度、启动已停止设备）：执行前必须征得用户
  确认（FR-008,2026-08-22 起确认门覆盖全部操作）。
- 用户附近无售后网点或位置信息不可用：系统应提供品牌官方客服联系方式作为兜底。
- 诊断信息正常但用户仍报告问题存在（故障不可复现）：系统应给出观察建议并记录，
  而非强行执行修复。
- 修复会话中途用户离开或会话超时：系统应保留会话记录，用户返回时可查看当前
  状态与结论，不得悬空执行未完成的修复动作。
- 注册账号已存在 / 两次密码不一致 / 账号或密码不满足校验规则：拒绝并说明
  具体原因，不泄露账号是否已注册之外的额外信息。
- 被禁用（逻辑删除）用户：登录拒绝；已签发的令牌立即失效，进行中的会话不受
  追溯影响。
- 登录令牌过期或注销后继续使用：一律按未登录处理（401）。
- 初始管理员账号：经种子数据创建（data.sql，缺省密码部署后必须修改）；
  注册接口 MUST NOT 允许自选角色，新用户一律为普通用户。
- 用户添加的 SN 已存在于本平台设备列表：无论该设备当前绑定哪个用户，系统都 MUST
  拒绝重复添加并返回 SN 已绑定错误，不得新增或覆盖绑定记录。
- SN 查询返回设备存在，但其类型或型号当前不在诊断支持范围：系统仍应将设备加入用户的
  设备列表；用户发起诊断时再明确提示暂不支持，不得尝试读取诊断信息或执行修复。
- SN 不符合接口规定的格式：系统应提示 SN 格式不合法；查询返回 `exists: false`：系统应
  提示“设备不存在或不在线”；查询超时或设备服务返回 5xx：系统应提示“设备服务暂不可用，
  请稍后重试”。以上情况均不得新增设备或绑定记录。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接受用户的自然语言问题描述作为输入。
- **FR-002**: 系统 MUST 从用户输入中提取关键属性：设备类型与问题表现（含复现
  方式，若有）；信息不足时 MUST 向用户追问澄清。
- **FR-003**: 系统 MUST 根据提取的属性在用户已接入的设备中定位目标设备；存在
  多个候选时 MUST 要求用户确认唯一目标。
- **FR-004**: 系统 MUST 判断目标设备类型和型号是否在受支持清单内；任一不在清单内时 MUST
  明确告知并给出替代建议，不得尝试诊断或修复。
- **FR-005**: 系统 MUST 能向目标设备请求基础诊断信息（本期经 deviceSimulator
  读取设备 state，如亮度/色温/运行状态，具体项随设备类型而定）。
- **FR-006**: 系统 MUST 结合用户问题描述与诊断信息推断设备问题，并给出可理解的
  问题结论；故障判定规则 MUST 配置化（设备注册表），规则结果覆盖三类：可自动修复、
  不可自动修复（含人工步骤或转售后）、无异常（2026-08-27 澄清）。
- **FR-007**: 系统 MUST 基于问题结论从解决方案知识库中检索匹配的修复方案。
- **FR-019**: 系统 MUST 按客户问题意图进行路由:(1) 常识性问题→直接回答,不触碰  任何设备;(2) 可自动修复/自动操作的问题→进入诊断修复流程(调用探测与操作工具,
  操作前确认见 FR-008);(3) 型号特异性问题→本期并入(1)直接回答,型号 RAG 知识库
  后续作为准确率增强接入(2026-08-22 澄清);(4) 网点查询→查询并返回售后网点信息
  (本期由项目内固定 mock 数据生成网点列表,后续仅替换查询实现为地图搜索工具)。
  意图无法确定时 MUST 追问澄清(复用 FR-002 机制),MUST NOT 在分类不确定时触碰
  设备。
- **FR-020**: 系统 MUST 提供设备添加能力：用户提交 SN 和设备名称后，系统 MUST 以 SN
  调用 deviceSimulator 的设备查询接口；仅当响应表明设备存在时，才可依据返回的设备详情
  将设备加入当前用户的设备列表，不得再调用 deviceSimulator 创建设备。SN 在本平台内
  MUST 全局唯一；若该 SN 已绑定任何用户，系统 MUST 拒绝重复添加，不得新增或覆盖绑定记录。
  用户提交的设备名称 MUST 作为平台设备列表中的显示名称；查询响应的 `name` MUST 仅作为
  模拟器原始名称记录，不得覆盖用户提交的显示名称。设备添加与诊断支持范围 MUST 分离：
  查询到的设备即使类型或型号当前不受支持，也 MUST 加入设备列表；仅在用户发起诊断时
  按 FR-004 拒绝诊断并提示暂不支持。SN 格式不合法时，系统 MUST 返回明确的格式错误；
  查询响应为 `exists: false` 时，系统 MUST 提示“设备不存在或不在线”；查询超时或设备服务
  返回 5xx 时，系统 MUST 提示“设备服务暂不可用，请稍后重试”。任何查询未成功确认设备
  存在的情况都 MUST NOT 写入设备或绑定记录。成功添加时，系统 MUST 持久化模拟器设备 ID、
  SN、设备类型编码与 ID、设备型号编码与 ID、模拟器原始名称以及用户提交的显示名称；
  MUST NOT 持久化查询响应中的 `state`、`running_status`、`created_at` 或 `updated_at`，设备
  运行信息 MUST 在诊断等需要使用时从 deviceSimulator 重新查询。
- **FR-021**: 系统 MUST 支持以 SSE(Server-Sent Events）向调用方流式推送处理过程：
  发起会话与追加消息接口 MUST 返回 text/event-stream 流，流内包含 LLM 生成内容的
  逐 token 文本事件与状态机关键节点事件（状态迁移/等待确认/终态结论）;
  进入等待用户输入态或终态时 MUST 主动结束流；断线 MUST NOT 补发事件，
  调用方经 GET 会话端点补查状态（2026-08-27 澄清）。
- **FR-008**: 对可自动执行的修复方案，系统 MUST 能向设备下发修复操作；所有改变
  设备状态的操作 MUST 先获得用户确认（2026-08-22 澄清：确认门从"仅中断型操作"
  扩为"全部操作"；仅读取诊断信息的探测无需确认）。
- **FR-009**: 修复执行完毕后，系统 MUST 再次获取设备诊断信息进行复检，并向用户
  输出明确结论：已修复（含修复内容）或未修复（含原因）。
- **FR-010**: 无法自动修复且有明确人工步骤时，系统 MUST 告知用户无法自动修复的
  原因与分步操作指引。
- **FR-011**: 无法自动修复且无明确步骤时，系统 MUST 基于用户位置查询并提供附近
  售后网点的名称、地址与联系方式；位置不可用时 MUST 提供官方客服渠道兜底。
- **FR-012**: 系统在技术架构上 MUST 支持后续新增设备类型的扩展：新增设备类型时
  MUST NOT 修改核心诊断修复流程，仅需补充该设备类型的诊断项、可执行修复动作
  与解决方案知识（本特性仅交付智能灯泡——经 deviceSimulator 模拟器接入；
  路由器、空调待模拟器扩展对应型号后接入（2026-08-27 澄清），扩展能力为架构约束）。
- **FR-018**: 对话（会话）管理:每个对话以 session id 唯一标记并长期保留;用户
  MUST 能查看本人历史对话列表、选择新建对话或继续已有对话;终态对话可继续——
  用户在同一对话线程内提出新问题时,状态机 MUST 从终态进入新一轮分析
  (终态→ANALYZING 回路);继续对话时最近 20 条历史消息 MUST 对新输入的分析与
  诊断可见(LLM 端对话记忆,超出窗口的消息仍长期留存可查)。
- **FR-013**: 系统 MUST 记录每次诊断修复会话的关键过程（输入、诊断结果、执行的
  修复动作、复检结论），用于追溯与知识库改进；对话记录长期保留，不设删除期限
  （2026-08-22 澄清：撤销原 90 天清理策略）。
- **FR-014**: 设备不可达（离线/超时）时，系统 MUST 终止诊断流程并提示用户检查
  设备电源与网络，不得继续执行修复。
- **FR-015**: 系统 MUST 要求用户登录后使用本功能；设备与用户账号绑定，用户 MUST
  只能诊断与修复本人名下的设备，对越权请求 MUST 一律拒绝并提示。
- **FR-016**: 同一台设备同一时间 MUST 只允许一个进行中的修复会话（设备级互斥）；
  对该设备的新请求 MUST 被拒绝并提示"该设备正在处理中，请稍后再试"，MUST NOT
  并发执行修复操作。
- **FR-017**: 修复操作执行失败（含中途失败）时，系统 MUST 立即停止后续动作，
  MUST NOT 自动重试；随后 MUST 复检设备当前状态，如实告知用户失败情况与设备
  现状，并转入人工引导分支（FR-010/FR-011）。
- **FR-022**: 系统 MUST 提供用户注册：用户提交账号、密码、确认密码；账号唯一，
  两次密码不一致或校验不通过时 MUST 拒绝并说明原因；密码 MUST 加密存储，
  任何接口/日志 MUST NOT 输出明文密码。校验规则（2026-08-29 澄清）：账号
  4~32 位（仅限字母/数字/下划线）；密码 8~64 位且须同时含字母和数字；密码
  经 BCrypt 加密存储；昵称缺省取账号。
- **FR-023**: 系统 MUST 提供用户登录：账号+密码校验通过后签发登录令牌——
  随机 token 存 Redis（带过期时间），调用方经请求头
  `Authorization: Bearer <token>` 携带；账号不存在或密码错误 MUST 拒绝
  (2026-08-29 澄清：Redis 令牌形态）。dev-mode `user-{id}` 令牌保留为显式
  开关（`AUTH_DEV_MODE`，默认开、生产 MUST 关闭），开启时仍可用于本地/测试，
  真实 Redis 令牌始终优先解析（2026-08-29 澄清）。
- **FR-024**: 系统 MUST 提供获取当前登录用户信息：依据请求令牌返回该用户的
  账号信息（脱敏，不含密码）；令牌无效/过期 MUST 按未登录处理。
- **FR-025**: 系统 MUST 提供用户注销：删除 Redis 中的登录令牌，注销后该令牌
  MUST 立即失效。
- **FR-026**: 用户分普通用户（user）与管理员（admin）两种角色；管理员额外拥有
  管理其他用户的权限；普通用户与管理员均 MUST 只能看见并操作本人的设备列表
  与对话（FR-015 越权约束不变）。
- **FR-027**: 管理员用户管理仅限最小集（2026-08-29 澄清）:用户列表（分页、
  按账号/昵称搜索）+ 禁用/启用（逻辑删除标记）；被禁用用户的登录令牌 MUST
  立即失效且不可再登录；本期 MUST NOT 提供修改角色与重置他人密码的接口；
  管理接口 MUST 仅管理员可访问，普通用户访问 MUST 拒绝（403）。

### Key Entities

- **问题报告 (Problem Report)**: 用户的一次求助，包含原始描述、提取出的设备类型、
  问题表现/复现方式、追问澄清记录。
- **设备 (Device)**: 用户已接入的物理设备，持久属性包含全局唯一 SN、用户设置的平台
  显示名称、模拟器原始名称、设备类型编码与 ID、设备型号编码与 ID、模拟器设备 ID 和
  所属用户；`state`、`running_status` 与模拟器时间戳不持久化，按需实时查询。设备类型和
  型号决定其诊断项与可执行修复动作。
- **诊断快照 (Diagnostic Snapshot)**: 某时刻从设备采集的基础诊断信息集合，用于
  修复前的定位与修复后的复检对比。
- **修复方案 (Repair Knowledge)**: 知识库中的条目，关联问题特征、解决方案内容、
  是否可自动执行、人工操作步骤。
- **修复会话 (Repair Session)**: 一次完整的诊断-修复流程记录，串联问题报告、
  目标设备、诊断快照、执行动作与最终结论。
- **售后网点 (After-sales Location)**: 品牌售后服务点，包含名称、地址、联系方式、
  覆盖区域。
- **用户 (User)**: 平台账号，包含账号（唯一）、加密密码、昵称/头像/简介、
  角色（user/admin）、逻辑删除标记；设备与对话均归属用户。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从输入问题到收到首个诊断结论的时间不超过 2 分钟（设备可达时）。
- **SC-002**: 对受支持设备类型的常见可自动修复故障，自动修复成功率不低于 70%。
  （本期不作量化验证，仅通过手动场景验证可行性；故障清单与统计口径待知识库
  案例丰富后补充——见 Clarifications 2026-08-22）
- **SC-003**: 对不在支持范围内的设备描述，系统 100% 明确拒识，不发生误诊或误操作。
- **SC-004**: 用户输入无法唯一确定目标设备时，系统 100% 要求澄清后再执行任何
  设备操作。
- **SC-005**: 无法自动修复的场景中，100% 的用户能收到可执行的下一步指引
  （人工步骤或售后信息）。
- **SC-006**: 新增一种设备类型所需的改动不涉及核心诊断修复流程，配置化接入
  可在 1 个工作日内完成。
- **SC-007**: 90% 的用户无需人工客服介入即可完成一次完整的诊断修复会话
  （含被正确引导至人工步骤或售后的情况）。
- **SC-008**: 未登录或令牌失效的请求访问受保护接口 100% 返回 401；普通用户
  访问管理接口 100% 返回 403；任何用户访问他人设备/对话 100% 被拒绝。
- **SC-009**: 对有效、可发现且未绑定的 SN，设备添加成功率为 100%，设备列表准确展示
  用户设置的名称以及设备类型和型号；对重复 SN、无效 SN、不可发现设备或查询失败，
  新增设备和绑定记录数为 0。

## Assumptions

- 用户设备已事先存在于 deviceSimulator；本平台 device 表维护与用户账号的绑定关系，
  并记录 SN、模拟器设备 ID、设备类型/型号编码与 ID、模拟器原始名称和平台显示名称，
  不持久化运行状态与设备状态。设备添加接口按 SN 查询可发现设备后写入绑定，不负责在
  deviceSimulator 中创建设备；SN 在本平台内全局唯一（2026-09-04 修订）；
  用户账号体系由本特性交付（US3：注册/登录/注销，Redis 令牌，2026-08-29 新增，
  取代"平台已有登录体系"的旧假设与 dev-mode `user-{id}` 令牌——dev 令牌去留见
  澄清）。
- 每类受支持设备提供获取基础诊断信息与执行修复操作的既有能力，本特性只做
  编排与决策，不实现设备侧固件能力。设备交互通过 HTTP 调用外部设备服务;
  **当前开发阶段对接独立的 deviceSimulator 模拟设备服务(默认 localhost:8081,
  接口契约见仓库根《后端接口说明.md》),设备交互唯一实现为 HTTP 客户端,
  原项目内硬编码 mock 撤销**(Clarifications 2026-08-27,修订 2026-08-22 决定)。
- 解决方案知识库已有首批内容（覆盖智能灯泡常见故障；路由器/空调知识随模拟器
  型号扩展后补充），知识库的持续运营不在本特性范围内。
- 售后网点数据来自外部查询服务，本特性只消费查询结果；用户位置默认由用户
  在会话中提供或经授权获取。
- 首期仅以 API 形式交付（纯文字对话式交互），不提供任何用户界面；交互界面由
  调用方自行实现。语音/图片输入不在本期范围。
- 修复动作可能中断服务时的确认默认在对话内完成，无需额外的审批机制。
