# Feature Specification: 设备故障诊断

**Feature Branch**: `001-iot-auto-diagnosis`

**Created**: 2026-08-21

**Updated**: 2026-09-07

**Status**: Draft — 已拆分为独立诊断 feature，原实施计划需按新边界重新规划

**Input**: 用户通过自然语言描述设备问题；AI 负责理解症状、检索知识、组织信息和诊断推理。诊断采集只读设备信息并给出结论与建议；可执行修复方案生成待确认控制请求，由独立安全控制流程完成后续操作。

**Feature Map**: [五个 feature 总览与原需求迁移映射](../README.md)。原混合规格及历次澄清保存在[拆分前规格](history/20260907-before-feature-split.md)；本文件为当前诊断范围。原 FR 编号在仍归属诊断的要求中保留，其余要求迁入对应 feature。

## Clarifications

### Session 2026-09-07

- Q: 故障诊断发现可执行的修复方案后，应如何衔接设备控制？ → A: 诊断生成待确认的控制请求，交给独立的安全设备控制 feature 统一完成权限检查、参数校验、用户确认、执行、审计和复检；按公共基础与统一路由、知识咨询、设备信息与状态查询、故障诊断、安全设备控制五个 feature 拆分并更新规格。
- 延续已确认的诊断约束：只操作本人已绑定设备；首期支持独立 deviceSimulator 中的智能灯泡；规则配置化；诊断信息只读采集无需额外操作确认；无法远程修复时提供人工步骤或售后引导。
- 原“诊断与控制合并为 DEVICE_ACTION”的路由规则由公共基础的四能力分类取代。长期会话、最近 20 条历史、账号、SN 绑定和流式响应由公共基础统一维护，诊断不再独立建设这些模块。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 获得有依据的设备故障诊断 (Priority: P1)

用户描述“客厅灯不亮”或“客厅灯太暗”，系统定位本人设备、检查诊断支持范围并采集只读状态，结合配置规则和维修知识给出故障结论、依据与建议。

**Why this priority**: 即使不执行设备操作，用户也能知道发现了什么、是否可修复及下一步怎么做，诊断可独立交付价值。

**Independent Test**: 在真实外部设备服务中准备受支持灯泡的异常与正常状态，输入对应问题；验证证据、规则、结论和修复候选，设备命令下发次数为零。

**Acceptance Scenarios**:

1. **Given** 本人灯泡可达且亮度命中配置化异常规则，**When** 描述“客厅灯太暗”，**Then** 读取本轮真实状态并检索适用方案，说明异常证据和可执行修复候选；诊断自身不下发调亮度命令。
2. **Given** 多台本人设备符合描述，**When** 无法唯一确定目标，**Then** 列出候选并追问，在目标明确前不采集实时诊断信息。
3. **Given** 本人已绑定设备不在诊断支持清单，**When** 发起诊断，**Then** 明确提示类型/型号暂不支持并给出替代建议，不采集诊断信息；仍可通过设备查询 feature 查看稳定元数据。
4. **Given** 本轮状态正常但用户仍报告异常，**When** 规则和已有证据无法复现故障，**Then** 说明未发现异常和证据局限，给出观察/补充信息建议，不强行生成修复操作。
5. **Given** 用户未登录或目标属于他人，**When** 发起诊断，**Then** 拒绝访问，不泄露或采集该设备状态。

### User Story 2 - 将修复候选移交安全控制 (Priority: P1)

诊断发现允许的远程修复候选后，用户看到独立安全控制流程的确认说明；确认后收到执行与复检结果形成的诊断结论。

**Why this priority**: 保留已有闭环体验，同时确保诊断推理不能直接导致设备状态变更。

**Independent Test**: 验证诊断生成和移交候选的内容及来源关联；控制能力可通过约定结果替身验证交接，完整闭环另用真实设备验收。

**Acceptance Scenarios**:

1. **Given** 诊断发现有适用的允许动作，**When** 生成修复方案，**Then** 将目标、候选动作、参数、诊断依据和轮次关联交给安全控制；控制流程重新校验并等待用户确认。
2. **Given** 用户未确认、拒绝或取消，**When** 结束本轮处理，**Then** 保留诊断结论并说明操作未执行，不能显示已修复。
3. **Given** 控制流程返回执行成功且复检证实预期状态，**When** 组织最终回答，**Then** 说明实际操作与复检依据，可据此报告已修复。
4. **Given** 控制执行失败、设备不可达或复检无法确认，**When** 回传诊断，**Then** 如实说明未修复或无法确认及下一步，不自动重试、不改用其他写入口。
5. **Given** 安全控制能力当前未交付或不可用，**When** 诊断得到修复候选，**Then** 仍返回诊断与建议，并明确当前无法提交执行；不假装已移交或已完成修复。

### User Story 3 - 获得人工步骤与售后引导 (Priority: P2)

问题不能远程修复时，用户获得已知人工操作步骤；缺少明确步骤时，获得售后联系渠道。用户明确查询售后时，可直接进入该分支。

**Why this priority**: 无法自动处理的故障也应有清晰下一步，不迫使用户重复描述问题。

**Independent Test**: 使用规则可确定的不可远程修复状态及固定售后数据，验证人工步骤、网点和无位置/无匹配兜底，不依赖成功控制路径。

**Acceptance Scenarios**:

1. **Given** 规则与适用知识给出明确人工步骤，**When** 判定无法远程修复，**Then** 解释原因并提供分步指引，不自动执行其中涉及设备变更的动作。
2. **Given** 无明确可行步骤，**When** 用户提供位置，**Then** 返回可用网点的名称、地址和联系方式；首期模拟数据必须标识为示例。
3. **Given** 位置不可用、无匹配网点或售后服务失败，**When** 组织引导，**Then** 提供已配置的官方客服渠道；若无可靠渠道数据则说明缺失并建议查阅品牌官方资料，不编造电话或地址。
4. **Given** 用户明确询问售后网点，**When** 公共入口分流到本分支，**Then** 仅补充所需品牌/位置等信息，不为查询网点而先探测或控制设备。

### Edge Cases

- 模糊设备、症状或复现条件先追问；单轮多个独立问题/多设备诊断先选定一项，不自动并行操作设备。
- 状态不可读或外部服务超时：终止依赖该证据的诊断，说明当前无法判断，不推测设备一定离线或伪造诊断成功。
- 规则未匹配、知识无结果或 AI 结论与实际状态/允许动作冲突：说明依据不足，给出补充信息或人工引导，不由 AI 自行开放新命令。
- 在诊断中检索到的知识、设备名称或用户输入包含控制指令，不得绕过安全控制的校验与确认。
- 设备正被其他互斥流程占用：明确提示处理中；当前诊断、移交和终止按共享占用规则协调，不误释放其他流程占用。
- 会话终态后继续提问由公共入口重新路由；本轮不能使用其他轮次的快照、控制确认或结论替代当前证据。
- 用户离开、取消或等待超时：保留已形成的结论，不在后台启动未经确认的修复。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-002**: 系统 MUST 从诊断输入中提取设备线索、问题表现及可用复现条件，缺少影响判断的必要信息时追问，不要求与诊断无关的额外信息。
- **FR-003**: 系统 MUST 在当前用户已绑定设备中定位唯一目标，采集前校验归属；多个候选时由用户澄清。公共定位与权限能力必须复用，模型提供的目标不视为已授权目标。
- **FR-004**: 系统 MUST 在读取诊断信息前校验类型/型号是否受支持，不支持时明确拒绝诊断并给出替代建议；此限制不阻止设备绑定、稳定元数据查询或有依据的知识咨询。
- **FR-005**: 系统 MUST 读取目标设备当前可用的只读诊断信息，记录本轮采集时间与来源；不能用绑定时信息或上轮快照伪装为当前状态。
- **FR-006**: 系统 MUST 结合用户描述、实际诊断信息、配置化故障规则和适用知识形成可理解结论，区分可提出远程修复候选、不可远程修复、未发现异常和证据不足。规则用于约束允许结果和动作，AI 负责解释和推理，不能放宽规则。
- **FR-007**: 系统 MUST 基于问题与设备适用范围检索已有维修知识，关联所用知识依据；未找到时说明缺失，不编造方案、来源或设备能力。
- **FR-008**: 存在可执行修复候选时，诊断 MUST 生成待确认控制请求，包含目标、候选动作与参数、依据和会话轮次关联，交给[安全设备控制](../005-safe-device-control/spec.md)重新校验、展示并确认；诊断 MUST NOT 直接下发设备写命令。
- **FR-009**: 诊断 MUST 根据安全控制返回的执行与复检事实组织修复结论，区分已修复、未修复、未执行和结果无法确认；仅收到命令受理或模型推断不能宣称成功。
- **FR-010**: 无法远程修复且有适用人工步骤时，系统 MUST 说明原因并提供分步指引；步骤只是建议，不授予任何自动设备写权限。
- **FR-011**: 无明确人工步骤时，系统 MUST 提供售后引导，可询问位置并返回可靠网点信息；位置/网点不可用时优先提供已配置官方渠道，不得编造。明确的售后查询可直接进入本分支。
- **FR-012**: 新设备诊断 SHOULD 通过补充诊断项、规则、适用知识及已有适配扩展契约接入，MUST NOT 为单一新型号重写通用诊断流程；首期仅交付当前受支持智能灯泡。
- **FR-014**: 设备信息获取失败时，系统 MUST 停止依赖该信息的诊断并提供检查建议，MUST NOT 继续生成需假定状态正常的执行请求或虚报诊断结果。
- **FR-016**: 诊断 MUST 复用既有设备互斥约束并与安全控制协调；同一设备已有冲突处理时提示稍后再试，诊断移交不能造成同时执行或误释放占用。
- **FR-028**: 诊断 MUST 关联保存原始问题、必要澄清、目标设备、当前轮次快照、规则与知识依据、诊断结论及控制请求/回传结果，复用公共会话与已有诊断数据模型。
- **FR-029**: 诊断 MUST 可在无设备写操作的情况下独立完成结论和建议交付；安全控制不可用时明确说明未移交执行，不影响输出已有诊断结果。
- **FR-030**: 诊断 MUST 复用公共 AI Service、配置、路由和流式响应；AI 输出候选和解释，服务端校验目标、规则与允许能力。AI MUST NOT 绕过权限、校验、确认和审计直接控制设备。

### Key Entities

- **问题报告**: 原始描述、设备线索、症状、复现条件及必要澄清，关联用户、对话和当前轮次。
- **设备**: 复用公共基础的绑定记录及支持信息，不在诊断中另建台账。
- **诊断快照**: 当前轮次的实际状态、采集时间、设备与来源，用于结论和后续复检对照。
- **维修知识**: 复用已有适用问题、方案、人工步骤和允许动作关联；知识内容不是执行授权。
- **诊断结论**: 发现、证据、依据局限、可修复性、建议及可选控制候选，必须与执行结果区分。
- **控制交接关联**: 本轮诊断到独立控制请求的关联，以及返回的执行与复检事实；确认与执行状态由控制 feature 负责。
- **售后渠道**: 网点、联系方式、适用区域及数据来源/示例标记。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 设备可达的诊断验收场景，从用户提供充分信息到首个诊断结论不超过 2 分钟，不包含等待用户补充或确认的时间。
- **SC-003**: 不支持类型/型号的诊断请求全部在采集前明确拒绝；越权设备信息读取和诊断自身的设备写调用均为零。
- **SC-004**: 无法唯一定位目标的验收场景全部先澄清，本轮快照和其他用户/轮次数据串用为零。
- **SC-005**: 无法远程修复的验收场景全部获得人工步骤、可靠售后渠道或明确的数据缺失与后续查找指引。
- **SC-010**: 可远程修复、不可远程修复、无异常、证据不足、设备不可达与知识缺失场景均有符合事实的结论和依据。
- **SC-011**: 所有修复候选均通过独立安全控制流程移交；未确认、取消、失败及复检不确定时，虚报已修复次数为零。
- **SC-012**: 诊断可在控制能力未启用时独立通过只读验收；完整闭环另行验证确认后执行与复检结果回传。

## Assumptions

- 依赖[公共基础](../002-assistant-foundation/spec.md)的用户、绑定、路由、AI Service、公共 DTO、会话和响应；复用当前问题分析、诊断推理、故障规则、维修知识与售后引导模块，不重建上述基础。
- 已有维修知识服务可独立复用；本 feature 不以[知识咨询](../003-iot-knowledge-assistant/spec.md)或[设备查询](../004-user-device-query/spec.md)对话入口全部交付为前提。读取使用共享设备客户端与适配能力。
- 当前设备交互使用独立 deviceSimulator，首期智能灯泡 LITE/LA001、LITE/LB001；项目内不新建设备模拟器。路由器、空调知识咨询可以按可靠资料回答，其诊断/控制接入不在本期。
- 故障通过真实设备状态与配置规则构造；原有规则、知识与集成场景可复用。模拟 AI 仅用于明确的测试模式，不作为真实 AI Service 交付证据。
- 首期售后沿用固定示例数据并明确标识；真实地图搜索、持续知识运营与新设备型号接入不在本次拆分范围。
- 原规格的“自动修复成功率 70%”“90% 无需人工客服”和“一工作日接入新类型”缺少当前可执行统计基线，不作为这次拆分的完成判据；未来取得故障样本和运营口径后再制定量化目标。现有手动场景验收仍保留，安全边界要求不降低。
- 原 plan、research、data-model、contracts、quickstart 和已完成 tasks 保留为拆分前资料；重新规划时按本规格和总览中的归属复用，不把历史任务完成状态当作新 feature 已交付。
