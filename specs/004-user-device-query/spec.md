# Feature Specification: 用户设备信息与状态查询

**Feature Branch**: `004-user-device-query`

**Created**: 2026-09-07

**Status**: Implemented, pending browser acceptance — 2026-09-22 已实现独立HTTP运行属性访问、更名后的本地Mock、部署级选择、四型号严格映射、字段诊断及确认/来源/重试/恢复保护。默认249项测试、非模拟器集成83项、前端构建及两种provider的可执行JAR四型号验收通过；不以HTTP夹具宣称物理设备实测。浏览器路由目视验收仍待完成。设计见 [plan.md](plan.md)，79项任务的当前勾选见 [tasks.md](tasks.md)，本轮及历史证据见 [validation.md](validation.md)。

**Input**: 用户通过自然语言查询本人已绑定设备的基础信息与实时信息。本服务维护用户的设备列表；基础信息包括设备型号、固件版本、在线状态，其中在线状态在流程启动时通过外部服务接口获取列表中各设备的状态，不以本地旧记录作为本次获取结果。基础信息查询不要求直接询问设备；实时信息则按设备能力向设备读取。每种型号通过统一设备能力模型声明 GET（只读属性/运行状态）、SET（可配置属性设置）、ACTION（执行一次设备操作）。AI 负责理解查询与组织结果，服务端负责权限、能力校验和真实数据访问。

**Feature Map**: [五个 feature 总览](../README.md)。依赖[公共基础与统一意图计划器](../002-assistant-foundation/spec.md)，复用已有设备管理和外部设备客户端。

## Clarifications

### Session 2026-09-07

- 设备信息与状态查询独立于知识咨询、故障诊断和设备控制。设备绑定成功不等于该设备的所有运行状态均可查询。
- 延续既有绑定规则：稳定元数据保存在平台，设备运行状态按需从外部服务获取；设备实时 GET 失败不推断为确定离线。2026-09-20 的启动在线状态加载另有明确规则：未获取到在线状态的设备按离线处理，并保留缺失或失败原因。

### Session 2026-09-15（历史决策，元数据确认约定已由2026-09-21替代）

- 除 2026-09-20 明确的意图规划前设备基础信息初始化例外外，设备查询及请求在执行前均需用户确认，包括元数据、实时状态、诊断取证和控制后复检；复检作为独立查询步骤，不能由诊断或控制隐式读取。确认可在同一步骤设备、操作与参数未变且有效时供重试/恢复复用，每次请求仍重新校验权限和幂等条件。
- 查询作为有序计划的独立步骤，支持前序结果引用和条件分支；超时有限自动重试，明确失败、拒绝或重试耗尽停止整个计划并保留已有结果；服务重启后仅本人明确请求继续才恢复。

### Session 2026-09-20

- Q: 当某型号的统一能力模型未声明某项 GET、SET 或 ACTION，但现有设备适配器支持它时，系统是否允许执行？ → A: 不允许执行；统一设备能力模型是执行允许清单，须先补齐该型号的能力声明；基础信息仍可在系统内查询。
- Q: 查询系统内保存的在线状态时，如果该记录较旧，应如何向用户展示？ → A: 在线状态由接口从外部服务获取；本服务维护用户的设备列表，流程启动时向外部服务请求列表中设备的在线状态，不采用仅展示本地旧记录的方案。
- Q: 流程启动时获取设备列表中各设备的在线状态，是否需要先取得用户确认？ → A: 无需确认，启动时自动获取，作为原确认规则的明确例外；设备实时 GET、SET、ACTION 仍须确认。
- Q: “流程启动时获取在线状态”是指每轮用户消息启动新工作流时，还是仅新建会话时？ → A: 每轮用户消息启动新工作流时获取一次；同一工作流的确认、重试、继续和恢复不重新触发初始化，复用已保存结果。
- Q: 启动时获取在线状态失败，或只返回部分设备的状态，是否应停止整个工作流？ → A: 不因初始化状态获取失败而停止工作流；保留已获取状态，缺失部分按离线处理。后续步骤若缺少必要条件或执行失败，仍按原规则停止整个计划。
- 补充要求：每轮新工作流在意图路由／意图规划前，自动获取当前用户所有已绑定设备的基础信息，包含设备 ID、名称、SN 号、设备类型、设备型号和在线状态，作为制定计划的依据之一；沿用已确认的初始化免确认、缺失在线状态按离线处理及同一工作流恢复复用规则。

### Session 2026-09-21

- C1=A：扩展现有 AiServiceAssemblyTest，验证提示词缺失、空白及变量不匹配时装配失败且模型调用为零。
- I1=B（用户回复“T1:B”）：首期mock只展示模拟属性、生成时间和来源；不基于模拟值解释、比较、估算或提出针对真实设备的建议，说明需要真实参数。通用知识咨询不受影响。
- G1=A：规划时检查字段/引用结构，解析设备后按精确型号GET定义检查字段；使用受控结果路径。每个型号须有明确绑定的结构化属性输出对象，结构一致时可复用；不能仅以任意Map代替型号契约。
- A1=A：确认授权读取该设备完整运行快照，列明全部GET及字段范围，绑定设备、操作、读取范围、能力内容hash和有效期；变化后重新确认。问题所需字段只影响回答展示，不缩小已经明确确认的完整快照范围。
- U1：不向设备请求数据的基础信息查询是plan前固定步骤，与用户问题一起输入Planner；信息足够时直接回答，不划分为DEVICE_QUERY，不生成list/metadata查询步骤，不要求设备查询确认。已保存在线快照仍来自初始化外部服务，未记录基础字段如实说明未知；不得为了回答补查设备运行属性。此决策替代此前元数据查询需确认的约定。
- Q: 新增的真实设备访问实现，应对接现有《设备操作接口说明》中的接口，还是其他设备接口？ → A: 按现有文档调用 `POST /device/{sn}/get` 获取运行属性，服务地址可配置；实际 HTTP 调用与本地 Mock 分为独立实现，连接模拟器时仍明确其数据来源。

### Session 2026-09-22

- Q: 本地 Mock 与外部设备访问应如何选择？ → A: 采用部署级配置，一次部署统一使用本地 Mock 或外部接口，切换配置并重启后生效，不按设备混用两种实现。
- 最新要求覆盖此前“规划前固定初始化”的触发时机：DeviceListTool 使用 @Tool 注入规划 AI Service，由 planner 决定是否查询列表。普通咨询不查设备；需要设备事实时才查询并在本流程复用。DeviceInfoTool 移除，实现下沉为 DeviceInfoService，仍在审批后调用。下文旧初始化表述保留历史上下文，当前行为以 FR-028–030 为准。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 初始化设备基础信息并直接回答 (Priority: P1)

用户询问已绑定哪些设备，或某台设备的名称、类型、型号、固件版本与在线状态。设备列表由本服务维护，在线状态来自流程启动时的外部服务查询；基础信息不通过设备实时属性 GET 获取。

**Why this priority**: 直接复用现有设备管理成果，提供自然语言查询价值。

**Independent Test**: 准备两名用户及各自绑定设备，验证流程启动时仅向外部服务查询当前用户设备列表中设备的在线状态；基础信息回答分别与本服务设备记录、本次外部服务返回值一致，缺失在线状态按离线处理且保留原因。不调用设备实时属性 GET，不泄露他人设备信息。已有基础信息足够时直接回答，设备查询步骤及其确认次数为零。

**Acceptance Scenarios**:

1. **Given** 用户绑定了多台设备，**When** 询问“我有哪些设备”，**Then** 返回本人的设备列表，使用用户设置的显示名称，并提供已知类型和型号。
2. **Given** 用户尚未绑定设备，**When** 询问本人设备列表，**Then** 明确说明列表为空，并说明可按现有流程添加设备，不编造设备。
3. **Given** 本人绑定了暂不支持诊断的型号，**When** 询问其名称和型号，**Then** 基于初始化快照直接返回稳定元数据，不生成设备查询步骤，并区分该信息与诊断/控制支持能力。
4. **Given** 用户提供他人设备 ID、SN 或名称，**When** 请求查询，**Then** 拒绝越权且不泄露该设备详情或所有者。
5. **Given** 当前身份和设备归属校验通过，本服务已维护本人设备列表及型号、固件版本信息，且外部服务提供在线状态，**When** 流程启动，**Then** 无需用户确认，自动按本人设备列表向外部服务获取在线状态；基础信息回答使用相应来源的数据，不调用设备实时属性 GET，也不要求存在该型号的 GET 声明。
6. **Given** 某项基础信息未记录或本次外部服务未返回某设备在线状态，**When** 用户查询该信息，**Then** 型号、固件版本等缺失字段明确说明未知；缺失在线状态按离线处理，并注明状态未获取、按离线处理的原因。不把本地旧在线记录冒充本次结果，也不为补齐信息隐式执行设备 GET。
7. **Given** 本人设备列表为空，**When** 流程启动，**Then** 不发起设备在线状态请求，不从外部服务扩展或推断其他设备归属。
8. **Given** 启动时已自动获取在线状态，**When** 后续计划准备读取设备实时属性或执行 SET／ACTION，**Then** 仍须对对应步骤取得用户确认，不能把在线状态加载视为授权。
9. **Given** 同一会话上一轮工作流已结束，**When** 用户发送新消息并启动新的工作流，**Then** 按当前用户设备列表重新获取本轮在线状态，不将上一轮结果作为本轮初始化结果。
10. **Given** 当前工作流已保存启动在线状态加载结果，**When** 用户确认、工作流步骤重试、继续或从检查点恢复，**Then** 复用该工作流保存的结果及原获取时间，新增初始化在线状态请求次数为零；恢复不意味着该结果已重新获取。
11. **Given** 外部服务仅返回部分设备的在线状态或本次加载全部失败，**When** 初始化结束，**Then** 保留已获取状态，未获取状态的设备全部按离线处理并记录原因，不因此停止工作流，不依赖这些设备在线状态的知识咨询等任务继续执行。
12. **Given** 初始化中某设备因缺失状态按离线处理，**When** 后续步骤必须满足设备在线条件但无法满足，**Then** 该步骤不得强行执行，报告原因并按原规则停止整个计划；初始化继续不等于免除后续条件校验。
13. **Given** 当前用户绑定多台设备，包含在线、离线及在线状态获取失败的设备，**When** 新工作流准备进行意图规划，**Then** 先完成基础信息初始化，再将全部本人设备的 ID、名称、SN 号、设备类型、设备型号和在线状态提供给意图计划器；缺失在线状态按离线处理且保留原因，不因设备离线而从规划依据中删除。
14. **Given** 当前用户未绑定任何设备，**When** 新工作流进入意图规划，**Then** 提供明确的空设备集合，允许继续规划知识咨询等不依赖设备的任务，不把空集合当作加载失败或编造设备。
15. **Given** 意图计划器已获得设备基础信息，**When** 生成并执行设备查询或控制步骤，**Then** 基础信息可作为规划及直接回答依据，设备操作执行仍需重新校验设备归属、能力和权限，并取得对应步骤确认；模型不能借此绕过安全边界。

### User Story 2 - 查询单台设备的实时状态 (Priority: P1)

用户询问“客厅灯亮度多少”“现在是否运行”，系统明确查询目标及范围，经用户确认后获取设备运行属性。在已有受型号能力约束的本地 Mock 之外，本次新增独立的外部设备访问实现；二者遵循同一服务接口、型号契约与安全边界，内部记录实际数据来源；对用户将外部模拟器按普通设备回答，不展示来源代码或模拟器提示。

**Why this priority**: 实时查询是独立能力，不应先要求用户描述故障。

**Independent Test**: 使用已绑定且在线的受支持型号，分别验证本地 Mock 和外部访问实现。Mock 属性满足对应能力定义且标记模拟来源；外部访问使用可控 HTTP 测试替身按已确认接口契约返回属性，验证目标 SN、数据映射、来源、错误和安全边界，不要求依赖运行中的设备模拟器。两种实现均不得下发命令。

**Acceptance Scenarios**:

1. **Given** 唯一匹配的本人在线灯泡有有效能力定义且使用本地 Mock，**When** 询问“客厅灯现在亮度多少”并确认该查询步骤，**Then** 返回本次生成的模拟值、生成时间和模拟来源，数值符合型号能力范围，不声称读取了真实设备亮度。
2. **Given** 有多台设备符合“卧室灯”，**When** 查询该设备状态，**Then** 列出本人候选设备并澄清，在目标唯一前不读取设备实时状态。
3. **Given** 设备服务超时或返回错误，**When** 查询状态，**Then** 仅超时可在公共预算和有效确认范围内自动重试；明确错误、拒绝或重试耗尽停止整个计划，报告状态无法获取并保留已有结果，不推断设备离线。
4. **Given** 当前设备或字段不支持状态读取，**When** 查询该字段，**Then** 明确说明不支持或无数据，仍可返回已知元数据；不推导不存在的指标。
5. **Given** 查询步骤用于诊断证据或控制后复检，**When** 计划路由到该步骤，**Then** 独立展示目标与读取范围并等待确认，不复用另一查询或控制步骤的确认；读取结果供后续步骤或主图汇总引用。
6. **Given** 同一步骤超时或中断后恢复，**When** 查询内容未变且确认仍有效，**Then** 可复用确认并校验当前权限，已成功结果不重复执行；重启后本人请求继续前不读取设备。
7. **Given** 适配器能够读取某字段，但当前型号的统一设备能力模型未声明对应 GET，**When** 用户请求该字段，**Then** 返回能力不支持并停止计划，不调用适配器读取该字段，不回退到其他型号能力。
8. **Given** 不同型号声明不同 GET 字段，**When** 分别查询各自支持的实时信息，**Then** 仅展示对应型号允许且通过校验的属性，本地 Mock 按该范围生成属性，外部访问映射接口实际返回值，不将某型号支持的字段自动视为其他型号也支持。

9. **Given** 用户只问亮度，**When** 准备查询，**Then** 确认界面明确显示将读取该设备完整GET快照及范围；确认后返回完整快照，回答可聚焦亮度，不能隐瞒实际读取范围。
10. **Given** 仅有mock参数，**When** 用户要求比较、估算或实际设备建议，**Then** 展示模拟来源并说明缺少真实参数，不输出基于mock的计算或物理结论；不会为了作答隐式发起新设备请求。
11. **Given** 净化器PM2.5或灯泡RGB嵌套字段在对应型号GET中已声明且有结构化输出映射，**When** 查询或引用前序结果，**Then** 通过受控路径校验；未声明字段、非法路径和类型不一致被拒绝。
12. **Given** 完整快照已获确认，**When** 能力内容hash或读取范围发生变化，**Then** 旧确认失效，实际读取前必须按新范围重新确认。
13. **Given** 使用外部访问实现且目标、权限、型号能力与完整快照确认均有效，**When** 执行运行属性查询，**Then** 按该设备 SN 调用现有设备操作接口，将返回属性校验并映射到型号结构化对象，保留实际来源及本次读取时间；内部保留模拟器来源用于审计，面向用户按普通设备自然语言回答。
14. **Given** 部署配置选择本地 Mock 或外部访问，**When** 服务启动并执行不同设备的运行属性查询，**Then** 全部使用所选实现，不按设备、用户或模型输出切换实现；配置切换在重启后生效，不在请求失败时自动切换。
15. **Given** 已有工作流在切换实现并重启后由本人请求继续，**When** 恢复已完成查询或尚待执行的查询，**Then** 已完成查询复用原结果、来源和时间；尚待执行的查询若实现或来源发生变化，旧确认不能直接用于新来源的请求，须展示变化并重新确认，仍按当前部署配置执行。

### Edge Cases

- 本人设备列表可包含多台设备；实时读取以一台已明确设备为一个逻辑步骤，多设备请求拆为有序且分别确认的步骤。
- 真实测得的“亮度为 3”是状态事实，不能自动等同于故障；“查询亮度，低于 30 就调到 80”生成查询及条件控制步骤，各自确认；查询步骤不自行升级为控制；首期mock不能作为真实控制条件的依据。
- 用户绑定的设备在外部服务中已不可发现：保留绑定记录，不自动删除、重新绑定或创建设备。
- 设备实时 GET 的字段缺失、类型不符合预期或响应不完整：明确指出无法确认的字段，不补造值。启动在线状态加载的缺失或失败按 FR-015 处理，不混用两类查询的失败语义。
- 用户身份在后续轮次失效或设备归属不再符合要求：重新校验并拒绝读取。
- 型号缺少能力模型或请求能力未声明：拒绝相应 GET／SET／ACTION，不能因适配器已有实现、AI 推测或用户确认而放行；不影响有权限的规划前基础信息初始化及基于该快照的直接回答。
- 同一会话可以包含多个工作流，启动在线状态加载以每轮新工作流为边界；页面刷新、重复确认和恢复已有工作流不构成新的加载触发条件。复用结果必须保留原获取时间，不因恢复而改写为当前时间；设备归属与权限仍须重新校验。
- 部署切换运行属性实现不改变已保存结果的来源，也不授权新的外部设备访问；恢复时须校验确认中绑定的实现和来源，不能沿用 Mock 查询的旧确认隐式发起外部请求。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持本人设备基础信息问答及设备运行属性查询，复用现有设备记录，不建立独立设备台账。基础信息在意图规划前固定加载，信息足够时直接回答，不属于DEVICE_QUERY；只有需要读取运行属性的请求才进入设备查询步骤。
- **FR-002**: 系统 MUST 使用经服务端确认的当前用户身份限制查询范围；用户输入、模型选择的设备 ID 或 SN 均不能绕过归属检查，管理员也不能查询他人设备。
- **FR-003**: 单台设备实时查询 MUST 先定位唯一的本人目标；候选不唯一或线索不足时先澄清，无绑定或无匹配时返回明确提示。
- **FR-004**: 基础信息 MUST 支持设备 ID、名称、SN 号、设备类型、设备型号、固件版本和在线状态。本服务 MUST 维护用户的设备列表；设备 ID、用户显示名称、SN 号、设备类型、型号和固件版本使用已有系统记录，在线状态 MUST 按 FR-014 从外部服务获取。基础信息查询仅可按 FR-014 执行在线探测，不得将响应中其他运行属性用于基础问答；型号、固件版本等字段未知时须明确说明，在线状态缺失按 FR-015 处理；未支持诊断、控制或未配置能力模型的设备仍可查询其基础信息。在线探测允许在授权前调用 POST /device/{sn}/get，但只保留 properties.online，其余属性不缓存、不持久化、不交给 AI，也不替代授权后的业务查询。
- **FR-005**: 设备在线信息（运行属性）MUST 由同一服务接口下相互独立的本地 Mock 与外部设备访问实现提供，区别于初始化在线布尔状态；本次 MUST 新增外部访问实现，不再仅保留未来替换入口。Mock 按精确型号 GET 定义生成参数，SN 不参与数值生成；外部实现按目标 SN 读取返回属性，不使用本地生成值冒充外部结果。两种实现均不得省略存在性、归属、在线及确认校验。MUST 内部保留实际数据来源和生成或读取时间；通过校验且来源一致的 REAL/SIMULATOR 属性均用于正常回答、分析及后续受控步骤，面向用户不显示 SIMULATOR 或相关提示。本地 MOCK、未知或冲突来源不得作为实际设备分析、控制条件或修复验证依据。
- **FR-006**: 运行属性查询 MUST 仅执行精确型号已声明且当前实现支持的GET，字段、类型、嵌套、枚举和范围须符合定义。每个型号 MUST 绑定结构化属性输出对象，结构相同可复用对象，仍按类型+型号明确注册及校验，不能借用其他型号能力。规划校验字段与前序结果引用的安全结构，解析设备后按型号校验真实字段；禁止固定全局字段白名单阻断合法型号字段或任意对象路径访问。
- **FR-007**: 系统 MUST 区分查询成功、无匹配设备、字段不支持、设备不可发现和服务不可用。设备实时 GET 失败不等于设备确定离线，部分字段缺失不能伪装成完整成功；对型号定义中已知的缺失或无效字段，MUST 保留安全字段路径及原因，并在步骤结果、历史和界面中说明具体无法确认的字段，不回显无效值或上游任意字段名。启动在线状态加载中未获取状态的设备按 FR-015 视为离线，MUST 保留该处理依据，不伪装成外部服务明确返回离线。
- **FR-008**: 本能力 MUST 只读。规划前基础信息初始化及基于已保存事实的直接回答无需设备步骤确认，不执行设备GET/SET/ACTION，不构成后续操作授权。运行属性、诊断取证和控制后复检 MUST 分别经用户确认；确认明确授权单设备完整GET运行快照，展示全部GET和字段范围，并绑定用户、计划、步骤、设备、操作、范围、能力内容hash和有效期。问题字段只影响回答展示。内容不变且确认有效时重试/恢复可复用；范围或能力版本改变须重新确认。每次实际请求重验身份、归属、权限及幂等，不得下发命令、修改绑定或自行升级为控制。
- **FR-009**: 系统 MUST 通过 QuerySubGraph 执行计划内的查询步骤，复用公共 AI Service、计划、会话与输出方式；AI 负责理解请求，系统组织可验证结果，确定性节点在确认及校验后读取并验证数据。查询结果 MUST 对外展示并供后续步骤引用，AI MUST NOT 改写数据来源或把mock作为真实测得值；完成后由主图推进计划。用于真实设备诊断、控制条件、控制参数或修复验证的设备结果及证据投影，其来源 MUST 完整、一致且为 REAL 或 SIMULATOR；冲突、缺失、未知或本地 MOCK 来源不得通过该门禁，不按当前部署配置修补来源。旧历史可只读展示，普通非设备结果不参与该设备证据校验。FR-014 的在线状态加载属于工作流初始化，其免确认和失败处理遵循 FR-008、FR-015，不视为普通计划查询步骤。
- **FR-010**: 用户可见查询结果 MUST 与本人会话、本轮设备及读取时间关联留存，MUST NOT 将临时状态写回稳定设备元数据。
- **FR-011**: 系统 MUST 支持初始化中加载多设备基础信息及计划内单设备运行属性查询步骤，多设备实时需求由公共主图编排为有序步骤，支持条件与前序结果引用，不自动增删或循环步骤。仅超时可按公共有限预算自动重试；明确失败、拒绝或耗尽即停止整计划并保留已有结果。幂等、检查点及重启后本人明确继续遵循 002；不包含历史趋势、订阅监控或跨用户查询。
- **FR-012**: 系统 MUST 以统一设备能力模型按型号维护能力声明，区分 GET（只读，获取设备属性或运行状态）、SET（修改设备可配置属性）、ACTION（执行一次设备操作）。该模型 MUST 作为能力执行允许清单：未声明的能力不得执行，已有适配器支持不构成例外；能力声明也不替代实际实现支持、权限、参数校验、用户确认和幂等检查。系统内基础信息查询不依赖 GET 声明。
- **FR-013**: GET MUST 保持只读；SET 与 ACTION MUST 作为独立设备控制步骤交由 005 的确定性安全控制流程执行，MUST NOT 在设备查询步骤中执行。模型统一描述三类能力，本 feature 负责基础信息和 GET 查询，SET／ACTION 执行仍由 005 负责。
- **FR-014**: 每轮用户消息启动新工作流时，系统 MUST 以本服务维护的当前用户设备列表为范围，自动通过外部服务接口获取列表中设备的在线状态，无需用户确认；不得查询他人设备或依赖外部服务结果自行增加用户设备。列表为空时不发起在线状态请求。在线状态结果 MUST 与设备、当前工作流及本次获取时间关联保存；缺失或失败按 FR-015 处理，MUST NOT 将本地旧值冒充本次外部服务返回值。同一工作流的确认、步骤重试、继续和检查点恢复 MUST 复用已保存结果及原获取时间，包括因缺失而按离线处理的结果，MUST NOT 重新触发该初始化；同一会话后续新工作流 MUST 重新获取。在线探测使用 POST /device/{sn}/get；响应必须包含匹配的 SN、success=true 和布尔 properties.online。404 为离线，协议无效、超时或其他失败按 FR-015 处理。该探测不依赖型号 GET 声明，只提取在线状态并丢弃其他属性，亦不授予后续查询或控制步骤执行权限；授权后的属性查询必须独立重新读取。
- **FR-015**: 启动在线状态加载失败或仅返回部分设备状态时，系统 MUST 保留已获取状态，将未获取在线状态的设备按离线处理，并继续工作流，MUST NOT 仅因该初始化获取失败触发整个计划停止。结果 MUST 区分外部服务明确报告离线与因状态缺失而按离线处理，保存并在展示该状态时说明缺失或失败原因。此规则仅适用于初始化在线状态获取，不豁免身份、归属、权限、结果持久化或后续步骤的执行条件；后续步骤缺少必要条件、明确失败、被拒绝或超时重试耗尽时，仍按公共规则停止整个计划。初始化的失败结果可供恢复复用，不得伪装成查询成功或设备实时测得值。
- **FR-016**: 每轮新工作流 MUST 在意图路由／意图计划器执行前，完成当前用户全部已绑定设备的基础信息初始化，提供包含设备 ID、名称、SN 号、设备类型、设备型号、设备在线状态六个字段的设备集合，作为用户消息及已有对话上下文之外的规划依据。在线状态按 FR-014/FR-015 获取和处理；离线或因状态缺失按离线处理的设备 MUST 保留在集合中，不得仅加载在线设备。无绑定设备时提供空集合；不得把设备列表加载失败伪装为空集合。初始化结果 MUST 按工作流保存，同一工作流继续或恢复时复用，不重复初始化。该集合与用户问题一同作为规划输入，并可作为直接回答基础信息问题的事实依据，不构成实时属性证据或操作授权，后续设备定位、权限、能力及确认校验仍须由服务端执行。意图计划器消费已加载信息；足够回答的问题走现有直接回答能力，不生成DEVICE_QUERY/list/metadata步骤。缺失基础字段说明未知、目标歧义时澄清，不自行执行设备访问。
- **FR-017**: 设备列表工具 MUST 接收用户 ID，返回该用户设备的 ID、名称、SN、类型、型号、在线状态和描述，并与设备列表页面共用响应服务；输入用户 ID 须与可信调用身份一致。无描述来源时返回空值，不编造设备描述；此前固件版本的基础查询仍在范围内，无记录时如实说明。
- **FR-018**: 设备信息工具 MUST 接收 SN 列表，仅返回输入 SN 对应的设备信息；每项包括基础信息、在线信息、能力信息和 errorCode。三类信息分别获取后拼装，基础信息与列表工具同源。不存在、不属于当前用户、离线分别返回 DEVICE_NOT_FOUND、DEVICE_FORBIDDEN、DEVICE_OFFLINE；无权设备不得返回名称、类型、型号、属性、能力或所有者资料，区分错误码不代表可读取其详情。图中多设备实时需求仍拆为独立且分别确认的步骤，不因工具支持列表而跳过逐步确认或失败停止规则。
- **FR-019**: 能力信息 MUST 由可替换服务提供，首期按设备类型与型号唯一定位静态 JSON，验证后载入缓存；工具可返回该文件的原始文本。缺失、类型/型号不匹配、定义无效时明确拒绝对应能力，基础信息仍可查询。服务须正确识别 GET、SET、ACTION，查询工具不执行 SET 或 ACTION。
- **FR-020**: 本期 AI 工具 MUST 继承 BaseTool 并位于 ai/tools，工具输入输出对象位于 ai/model；新增服务接口位于 service，具体实现位于 service/impl 且以 Impl 结尾。在线信息和能力信息均须提供 interface 与具体实现，工具不得绕过服务直接访问持久层或从请求参数接受可信用户身份。原在线信息 Mock 实现的类名与文件名 MUST 加入 Mock，以区别于独立的外部接口映射实现。
- **FR-021**: 外部运行属性访问 MUST 遵循 [设备操作接口说明](../../documents/设备操作接口说明.md)，通过 `POST /device/{sn}/get` 读取已确认单设备的完整属性，服务地址外部化配置。请求目标 MUST 来自服务端已校验的设备绑定及确认上下文；返回 SN 须与请求目标一致，属性须按精确型号 GET 定义和结构化输出对象校验。该接入不改变规划前基础信息初始化，不新增 SET／ACTION 执行能力；接口失败、字段缺失和超时遵循 FR-007/FR-011，MUST NOT 用 Mock 值补齐失败或缺失的外部结果。
- **FR-022**: 运行属性服务 MUST 通过部署级配置统一选择本地 Mock 或外部访问实现，切换配置并重启后生效；本期不提供按设备、用户或单次请求选择实现的能力，AI MUST NOT 决定实现选择，失败时 MUST NOT 自动切换实现。确认上下文 MUST 绑定并展示所选实现及数据来源；重试或恢复时二者不变且原确认有效才可复用确认，发生变化时须重新确认。已完成查询仍复用原结果、来源和时间，不因配置切换重新读取或重新标记；该选择不改变初始化在线状态的既有外部服务来源。

### Key Entities

- **设备绑定**: 复用平台设备记录，包含当前用户归属、唯一 SN、显示名称及稳定外部标识。
- **查询请求**: 运行属性查询类别、查询范围、目标线索、请求字段、计划与稳定逻辑步骤标识及该步骤确认关联；设备候选来自当前用户授权范围。
- **设备基础信息**: 型号、固件版本及已有名称/类型使用系统记录；在线状态来自每轮新工作流启动时按本人设备列表进行的外部服务查询，按工作流保存获取时间、结果及来源，区分外部服务返回状态与因缺失或失败按离线处理的状态，并保存原因。同一工作流继续或恢复时复用。与设备 GET 返回的实时属性或运行状态区分，字段缺失不触发隐式设备 GET。
- **规划设备上下文**: 当前工作流在意图规划前加载的本人全部设备集合；每项包含设备 ID、名称、SN 号、设备类型、设备型号、在线状态，并关联在线状态来源、获取时间和必要的失败原因。集合包含离线设备，按工作流留存并在恢复时复用；不替代执行时的权限和能力校验。
- **统一设备能力模型**: 某型号的能力声明集合，明确区分可获取信息的 GET、可配置属性的 SET 和可执行操作的 ACTION，作为查询与控制共同使用的执行允许清单，不等同于设备当前属性值或用户授权。
- **状态读取结果**: 指定设备本次读取的字段值、实际数据来源、生成或读取时间及缺失/失败原因，与稳定元数据分开；内部来源保留本地 Mock、外部模拟器及物理设备的区别用于审计；面向用户将外部模拟器按普通设备展示，不输出 SIMULATOR 或模拟器提示。
- **设备查询回答**: 经过校验的数据解释及可用性说明，不是诊断结论或控制请求。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 设备列表与单台元数据返回值与绑定记录一致；在线布尔状态有返回值时与外部服务一致，无返回值时按 FR-015 处理。首期 mock 运行属性全部满足型号能力定义并标识模拟来源，宣称为真实测量值的次数为零。
- **SC-002**: 除 FR-014/FR-016 的规划前基础信息初始化及基础事实直接回答外，运行属性查询在有效确认及校验完成前、单台查询目标未澄清前，业务设备读取次数为零；自动加载的越权请求及全部场景的越权设备详情泄露为零。诊断取证与控制后复检不得隐式绕过独立查询步骤。
- **SC-003**: 无数据、不支持字段、不可发现和服务失败样例全部给出对应提示，编造实时状态为零。
- **SC-004**: 全部查询场景的设备写操作与绑定记录变更次数为零；成功的实时回答全部带有本次读取时间。
- **SC-005**: 计划内查询步骤的超时重试未突破配置上限，明确失败/拒绝后的重试和剩余步骤执行次数为零；已成功查询的重复提交或恢复复用原结果，重启后明确继续前的查询执行次数为零。初始化在线状态获取失败按 FR-015 处理，不计为计划步骤失败。
- **SC-006**: 基础信息问答验收中，DEVICE_QUERY步骤、设备查询确认框、除 FR-014 在线探测外的业务设备 GET/SET/ACTION 调用次数均为零；回答与本轮初始化事实一致。初始化外部在线请求只覆盖本人设备，空列表请求为零；缺失/失败明确说明，不用旧值冒充本次结果，不以此免除运行属性步骤确认。
- **SC-007**: 能力模型缺失、能力未声明及仅适配器支持的 GET／SET／ACTION 验收中，对应设备调用次数为零；不同型号不互相借用能力声明，查询步骤执行 SET／ACTION 的次数为零；四型号的结构化输出映射与JSON字段一致，合法动态字段及嵌套结果引用通过，非法路径拒绝。
- **SC-008**: 同一会话连续两轮新工作流的验收中，每轮均针对当轮本人设备列表触发在线状态加载；已有加载结果的同一工作流在确认、步骤重试、继续及跨进程恢复时，新增初始化在线状态请求次数为零，保存结果及原获取时间完整保留。
- **SC-009**: 初始化在线状态全部失败及部分缺失的验收场景中，缺失设备按离线处理率为 100%，已有结果保留率及失败原因可追溯率均为 100%；仅因初始化获取失败而停止工作流的次数为零，不依赖缺失状态的知识咨询可继续。后续步骤因必要条件不满足而失败时，剩余计划步骤执行次数仍为零。
- **SC-010**: 多设备、离线设备、空列表和在线状态获取失败的验收场景中，设备基础信息初始化均先于意图计划器执行；规划输入的设备集合与初始化时本人绑定范围一致，六个规定字段全部提供，已有描述和固件信息作为补充事实；缺失值按对应规则明确表示，跨用户设备混入及漏掉离线设备的数量均为零。实际计划生成须使用该上下文，而非仅将其保存或记录日志；同一工作流恢复时不得重复加载已保存的设备基础信息。
- **SC-011**: 列表工具七个规定字段均提供；信息工具仅包含请求 SN 的结果，三种设备错误码准确区分；不存在、越权、离线设备的 mock 参数生成次数为零。有效能力定义的类型、范围、枚举与嵌套字段校验全部通过，无效资源不可用于生成参数；已提交结果的重试/恢复不重新随机生成数据；完整GET范围和hash展示并绑定确认，范围/hash变化后的旧确认执行次数为零。基于mock的解释、比较、估算、真实设备建议及控制条件执行次数为零。
- **SC-012**: 外部访问验收中，请求目标与已确认设备一致，通过校验的属性值与外部响应一致；目标不匹配或无效响应不得成为成功结果。除 FR-014 已获准的在线探测外，未确认、越权或能力未通过校验时外部运行属性请求次数为零；外部失败或缺失字段被 Mock 值替代、模拟器数据被宣称为物理设备实测值的次数均为零。原有本地 Mock 可独立验收。
- **SC-013**: 两种部署配置分别验收时，所有运行属性请求均使用所选实现，按设备混用及失败后切换次数为零。配置切换并重启后，新查询使用新实现；恢复已完成查询的新增读取及来源改写次数为零，未完成查询在实现或来源变化后未经重新确认的执行次数为零。

## Assumptions

- 002 提供账户、设备绑定、公共会话与路由；复用当前 `DeviceRegistryService`、`DeviceLocator`、设备归属校验和外部设备客户端，补齐自然语言字段查询与只读编排。
- 设备列表的在线状态继续来自既有外部设备服务；本项目不重建设备模拟器。本地 Mock 保留，本次新增遵循现有设备操作接口契约的独立外部运行属性实现；能力来源仍为 resources/device 的三类设备文件，只有类型、型号和内容校验通过的定义才可用于生成或校验属性。旧 LITE/LA001、LITE/LB001 未提供同名能力文件时仍支持基础查询，运行属性返回能力未配置，不静默映射到新型号。三类目录中四份现有文件的有效性及净化器错误文件处理见 [research.md](research.md)。
- 不要求先实现知识咨询、故障诊断或安全控制即可验收本 feature。各能力复用设备客户端与定位能力，避免通过“启动诊断流程”来查询状态。

## 2026-09-09 参数问答范围补充

基础信息问答先消费规划前固定加载的本人设备事实，信息足够即直接回答，不划入设备查询。只有需要读取运行属性的请求才生成DEVICE_QUERY。真实参数可用后的解释、比较、估算与建议保留为后续能力；首期mock仅展示模拟属性，对“亮度是否适合阅读”“估算实际耗电”等问题说明需要真实参数，不用模拟值计算或得出结论。通用知识和型号公开资料仍走003；显式状态变更必须独立进入控制流程，mock不能成为控制前置事实。


## 2026-09-22 设备目标规划增量

FR-023：查询和控制计划必须从本人设备快照确定 deviceRef，或引用前序设备步骤的 deviceRef。唯一匹配不索要 SN；歧义列出候选，无匹配说明未绑定。
FR-024：执行端只按计划引用校验快照成员、当前归属和绑定，不根据描述猜测；保留确认及执行前复核。
FR-025：规划澄清恢复保留原需求、历史及设备快照，结合新输入重新规划；已完成步骤不重跑，执行目标失效明确失败并提示重新发起。
FR-026：所有固定模型提示词的自然语言指令使用中文，保留协议标识。来源以实际结果为准。
FR-027：规划设备和已校验目标为强类型 state，schemaVersion=3；按需工具改造后的图版本为 assistant-v4，v1/v2/v3 图历史可读但不可执行。

验收覆盖自然语言唯一匹配、SN、历史指代、歧义澄清、多设备步骤、伪造与越权 ID、绑定变化、恢复及结果复用。Mock 与真实模型效果分别记录。

## Planner 按需工具调用（2026-09-22）

FR-028：图入口直接进入 IntentPlanner，不固定查询设备列表。DeviceListTool 通过 @Tool 注册到规划 AI Service，由模型决定是否调用；普通知识咨询不访问设备服务。
