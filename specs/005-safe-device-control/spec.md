# Feature Specification: 安全设备控制

**Feature Branch**: `005-safe-device-control`

**Created**: 2026-09-07

**Status**: Draft — 2026-09-15 同步多步计划、超时重试及独立复检查询；LangGraph4j 接入尚未实施，待独立规划。

**Input**: 用户可以通过自然语言提出设备控制诉求；所有设备状态变更 MUST 进入确定性控制流程，AI MUST NOT 绕过权限、校验、确认和审计直接控制设备。诊断可将修复候选交给同一流程处理。

**Feature Map**: [五个 feature 总览](../README.md)。依赖[公共基础与统一意图计划器](../002-assistant-foundation/spec.md)和既有设备适配能力；可独立于诊断接受直接控制请求。

## Clarifications

### Session 2026-09-07

- 用户已接受诊断生成待确认控制请求，交由独立安全控制流程完成权限检查、参数校验、用户确认、执行、审计和复检；直接控制请求使用完全相同的执行边界。
- 全部设备状态变更先确认及设备互斥约束继续适用；原“不自动重试”、隐式复检和禁止组合条件的限制，由下述 2026-09-15 规则取代。

### Session 2026-09-15

- 公共主图编排有序步骤、条件分支及前序结果引用；每个控制步骤只处理单台设备的一个动作，不自动增删或循环步骤。诊断候选可供已声明控制步骤引用，无对应步骤时重新生成计划。
- 同一步骤的设备、动作和参数未变且确认有效时，重试/恢复可复用确认，每次请求仍重新校验权限与幂等。仅超时可有限自动重试；明确失败、拒绝或耗尽即停止整个计划并保留已完成结果。无法保证幂等的结果不确定控制不得自动重发。
- 控制所需前置状态及执行后复检均由独立、需确认的查询步骤取得，不在 ControlSubGraph 内隐式读取；主图汇总控制与查询结果。重启后本人明确请求继续才恢复，已终止计划不可恢复执行。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 确认后执行明确的控制请求 (Priority: P1)

用户提出“把客厅灯亮度调到 80”，系统展示已校验的设备、动作、参数与影响，经用户确认后执行并报告实际结果。

**Why this priority**: 用户能够控制设备，同时每次状态变更均受可核对的服务端流程约束。

**Independent Test**: 使用真实外部设备服务中的本人灯泡，提出调亮度请求，验证确认前不执行、确认后只产生一次业务效果；最终状态由后续独立且再次确认的查询步骤读取，不需要先诊断故障。

**Acceptance Scenarios**:

1. **Given** 用户有权操作且目标唯一、动作与参数有效，**When** 请求调亮度到 80，**Then** 展示目标设备、动作、参数和影响，等待确认，设备尚未变化。
2. **Given** 当前请求正在等待确认，**When** 同一用户明确确认且执行前校验仍通过，**Then** 执行所确认的动作并返回实际执行结果和审计关联；主图推进到后续独立复检查询时重新等待该查询确认。
3. **Given** 用户拒绝或取消，**When** 流程继续，**Then** 停止整个计划，不下发命令并记录原因；仅确认过期且计划尚未终止时，须重新展示操作并确认后才能执行。
4. **Given** 参数超出设备支持范围或动作不在允许清单，**When** 用户请求执行，**Then** 明确拒绝或要求修正；不静默替换为另一动作，不因为模型认为合理就执行。

### User Story 2 - 接收诊断移交的修复请求 (Priority: P1)

诊断输出修复候选供计划内独立控制步骤引用，用户看到同一控制流程的确认说明；执行及后续独立复检查询的结果关联原诊断，由主图汇总。

**Why this priority**: 保留诊断修复闭环，避免建立一套可绕过安全约束的“自动修复”执行入口。

**Independent Test**: 提供包含诊断关联的修复候选，与直接控制请求走同一校验和确认路径；验证未确认、成功、执行失败与复检失败的结果回传。

**Acceptance Scenarios**:

1. **Given** 诊断移交某灯泡的调亮度候选，**When** 控制流程接收，**Then** 重新校验身份、归属、支持能力和参数，再展示待确认内容；诊断判断不等于授权。
2. **Given** 用户确认后动作成功且独立、已确认的复检查询值满足目标，**When** 主图汇总，**Then** 关联原诊断返回实际执行与复检证据，说明是否修复，不回跳诊断或由控制直接读取设备。
3. **Given** 命令超时、部分执行失败或复检不可用，**When** 处理结果，**Then** 超时仅在幂等有保障、确认有效及预算内自动重试；明确失败、拒绝或耗尽即停止整计划，如实保留已知结果，不声称已修复，也不为了复检继续已终止计划。
4. **Given** 用户单独提出有效控制请求，**When** 进入控制能力，**Then** 无需伪造故障、检索维修方案或启动诊断即可校验和确认。

### User Story 3 - 在异常与并发条件下保持控制边界 (Priority: P1)

用户在请求失效、并发操作或权限变化时收到明确结果，操作记录能说明实际发生了什么。

**Why this priority**: 正常路径之外仍须防止重复执行、越权和未经确认的动作。

**Independent Test**: 覆盖重复确认、设备互斥、确认后禁用用户、改参数、超时与恶意输入，核对实际命令次数及审计关联。

**Acceptance Scenarios**:

1. **Given** 同一控制请求已执行或执行中，**When** 重复确认、重复提交或客户端重连，**Then** 返回已有/进行中结果，不再次下发命令。
2. **Given** 设备已被另一控制流程或需要互斥的诊断流程占用，**When** 请求执行，**Then** 明确提示设备处理中，不并发执行；失败、取消或结束后释放属于本流程的占用。
3. **Given** 确认期间设备、动作或参数改变，或用户权限/登录有效性变化，**When** 收到旧确认，**Then** 拒绝旧请求；更新后的合法操作需要重新展示并确认。
4. **Given** 用户或知识文本要求忽略权限、直接调用设备命令，**When** 模型产出控制候选，**Then** 仍执行同一确定性校验，未通过不得下发。
5. **Given** 无法可靠记录待执行请求及确认/执行意图，**When** 准备下发命令，**Then** 不执行；若命令已发出后结果记录失败，保留待核对状态且不重复执行。
6. **Given** 同一步骤因超时重试或中断后恢复，**When** 操作未变且确认有效、权限和幂等校验通过，**Then** 可复用确认，所有尝试共享稳定幂等标识与总重试预算；已成功结果直接复用，重启后本人明确请求继续前不执行。

### Edge Cases

- 设备定位不唯一：只列出本人候选并追问，不能由模型替用户猜测目标。
- 普通问题、描述期望、“以后都同意”及其他轮次的“确认”不是当前明确操作的有效确认。
- 确认等待超时、会话中断后恢复或运行上下文丢失：旧请求不得自动执行；重新核对状态并获取必要的新确认。
- 请求在进入待确认阶段前必须有有效的校验结果；状态变化导致前置条件不再成立时，即使已有确认也不得强行执行。
- 命令已下发但响应丢失时，结果可能不确定；仅在外部幂等保障已验证且预算、确认、权限有效时允许超时重试，否则保留不确定状态并停止计划，不自动重发。核对设备状态须由另一独立且经确认的查询步骤完成；已停止计划不能为核对而继续，需用户发起新计划。
- 无法复检或状态未达到预期：区分执行失败、目标未达到和结果未知；用户收到下一步建议。
- 已发出的动作不追溯撤销；权限失效后不得继续启动新的动作。取消不意味着设备状态已回滚。
- 单设备互斥的共享机制由公共基础提供/复用，安全控制负责执行期间的获取、有效性检查和释放，不依赖提示词约束并发。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接收来自直接用户指令或故障诊断的控制候选，使用唯一的确定性设备控制流程；AI 仅负责理解和组织候选，MUST NOT 直接获得可绕过流程的设备写权限。
- **FR-002**: 控制候选 MUST 包含目标线索、一个动作及参数；服务端 MUST 定位唯一的本人设备。每个逻辑控制步骤仅处理单台设备的一个明确动作，多个动作/设备由公共计划拆为有序步骤，可按前序结果选择条件分支，MUST NOT 在执行中自动增删或循环步骤。
- **FR-003**: 服务端 MUST 校验当前身份有效、设备归属及操作权限；管理员没有隐含的他人设备操作权。用户输入或模型生成的身份与“已授权”标记均不可信。
- **FR-004**: 服务端 MUST 根据设备类型/型号、允许动作、参数类型与范围、必要状态前置条件校验请求；能力允许清单 MUST 使用 [004 定义的统一设备能力模型](../004-user-device-query/spec.md)，仅允许当前型号已声明且实际实现支持的 SET（属性设置）与 ACTION（一次设备操作）。未声明的能力即使已有适配器支持也不得执行。未知动作、缺参数、无效值和不支持能力均不可执行，MUST NOT 让 AI 自由生成设备接口或绕过允许清单；GET 属于独立只读查询。
- **FR-005**: 所有改变设备状态的动作 MUST 在完成初步校验后展示目标设备、动作、参数、预期影响并取得明确确认；任何默认同意或仅完成诊断均不满足确认要求。
- **FR-006**: 确认 MUST 绑定用户、会话轮次、计划、逻辑步骤、目标、动作、参数及有效期；同一步骤内容未变且确认有效时，超时重试或中断恢复可复用，不能跨步骤或新计划继承。拒绝、取消、过期或内容变化使原确认失效；合法更新或确认过期须重新校验和确认，拒绝/取消停止整计划。
- **FR-007**: 每次执行尝试前 MUST 再次核对权限、请求状态、确认有效性、设备支持能力及必要状态前置条件。所需状态 MUST 来自计划内独立且经确认的查询步骤，并校验时效；证据不足/过期时不得隐式补查或强行执行，需要新查询步骤时重新生成计划。
- **FR-008**: 同一设备 MUST 不并发执行互相冲突的操作，沿用共享互斥能力。重复确认/提交/恢复不得启动重复执行；符合 FR-010 的超时尝试 MUST 使用同一稳定幂等标识、预算和已持久化结果，MUST NOT 重复产生业务效果。
- **FR-009**: 命令 MUST 仅由 ControlSubGraph 内受控执行组件下发，AI 服务、知识咨询、设备查询和诊断均不得直接调用设备写路径。设备运行属性读取，包括前置取证及复检，MUST 使用独立且需用户确认的 QuerySubGraph 步骤，控制不能隐式读取。规划前基础事实可用于定位，不替代真实运行证据；004首期mock不能参与真实控制条件求值、前置状态判断或成功复检。
- **FR-010**: 仅请求超时且仍有公共重试预算、确认有效、当前权限通过、外部幂等有保障时，系统 MUST 有限自动重试并展示次数；下层重试共享该预算。明确失败、拒绝或耗尽 MUST 停止整个计划并保留结果及不确定性，后续查询/控制也不得执行；无法保证幂等的未知结果不得自动重发。MUST NOT 自动回滚、补偿写或恢复已终止计划。
- **FR-011**: 需要验证设备最终状态时，计划 MUST 声明控制之后的独立复检查询步骤，执行前取得该查询的确认；控制仅输出已知执行结果。复检缺失、未确认或计划提前停止时 MUST 说明状态未验证。主图根据已有控制和查询事实区分成功、失败、目标未达成和无法确认，MUST NOT 仅凭命令受理或模型文字声称修复成功。
- **FR-012**: 控制全程 MUST 关联记录用户、会话与轮次、请求来源、目标、动作和参数、校验结果、确认/取消/过期、执行尝试、时间、复检与最终结果；拒绝的请求也须可追溯，记录不得包含凭据或泄露他人设备信息。
- **FR-013**: 下发前 MUST 能可靠留存待执行请求、有效确认和执行意图；不能留存时不得下发。下发后记录失败 MUST 标记为待核对/结果不确定并阻止自动重放，不能将设备外部副作用当作可回滚的本地事务。
- **FR-014**: 诊断来源的控制结果及独立复检查询结果 MUST 关联原诊断步骤，由公共主图汇总；直接控制同样输出本步骤结果，不强制依赖诊断或维修知识，不由控制回跳诊断。
- **FR-015**: 系统 MUST 复用公共身份、会话、输出和设备客户端/适配器、执行与动作日志能力；取消、失效、结束和异常须按归属释放占用并保留结果。检查点覆盖等待确认、外部副作用边界和昂贵步骤；重启后仅本人明确请求继续未终止计划才恢复，原确认重新校验，已完成/终止计划不执行。

### Key Entities

- **控制候选**: 由用户诉求或诊断形成的候选设备、动作和参数，尚未获得执行授权。
- **控制请求**: 经服务端解析的用户、会话轮次、唯一目标、动作参数、来源和请求标识，以及校验/等待确认/执行中/结束状态。
- **确认记录**: 确认的确切内容、用户、计划、逻辑步骤、时间、有效期和失效原因；仅同一步骤未变且有效时供重试/恢复复用，不可跨步骤或新计划复用。
- **执行与审计记录**: 包含执行意图、下发尝试、返回结果、只读复检及最终状态；可复用既有动作日志与快照。
- **设备占用**: 当前流程对设备的互斥使用权，具有所属请求和有效性边界，不能由其他请求误释放。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 正常控制验收中，每次设备写操作均有对应的成功校验、有效确认及审计关联，覆盖率 100%；确认前命令次数为零。
- **SC-002**: 越权、未知动作、非法参数、取消、过期、旧确认、模型越界和审计准备失败场景的命令下发次数为零。
- **SC-003**: 重复提交/确认、超时重试及恢复场景中，同一逻辑控制步骤重复业务效果为零；幂等可验证时全部尝试共享标识和配置预算，同设备并发冲突次数为零。
- **SC-004**: 复检均通过独立查询步骤并取得该步骤确认；未复检、复检失败或未知结果时虚报修复成功次数为零；明确失败/拒绝/重试耗尽后，重试及所有后续步骤执行次数为零。
- **SC-005**: 诊断移交与直接控制均通过相同安全验收；全部已受理控制请求和校验拒绝可按请求追溯。

## Assumptions

- 首期设备范围沿用智能灯泡 LITE/LA001、LITE/LB001，仅执行统一设备能力模型已声明且既有注册表/外部服务支持的 SET／ACTION；现有能力须先补齐型号声明，不能仅以旧适配器支持放行。示例亮度 80 仅在设备范围允许时有效。
- 复用 `RepairExecutor` 中符合新安全边界的单操作能力、`DeviceLockService`、`RepairActionLog`、设备适配器与客户端；拆解并删除旧 `RepairExecutionRunner`，由ControlSubGraph承担控制流程，取证和复检必须进入独立查询步骤。现有实现需按本规格验证和补齐，不因原有任务勾选完成而视为安全边界已全部满足。
- 持久化遵循002的五类数据设计：command_execution保存控制命令的稳定身份、确认关联、尝试和结果确定性，audit_event复用repair_action_log追加事实；查询使用工作流步骤与审计。旧动作日志不是可恢复命令账本，重试/恢复复用同一逻辑命令，不能把审计SUCCESS或checkpoint存在当成外部效果成功。
- 公共基础提供统一 AI Service 与配置，控制候选作为结构化输出；具体确认字段、幂等标识、租约和持久化方案在本 feature 的 plan 中确定。
- 支持公共计划中的多设备有序步骤及条件分支；不增加一个步骤内的批量写、定时任务、长期授权、自动循环、动态增删步骤、设备固件实现或自动回滚。外部幂等能力须在 plan 核验，无法保障时安全保留未知结果，不能以重试实现重复副作用。
